Design — Toolchain & Initial Files

What gets created on day one, and why

Language & runtime

TypeScript — the only practical choice for VS Code extensions. The VS Code API ships its own type definitions, and strict TypeScript catches interface mismatches between your real and mock Jira clients at compile time (not at runtime). All official VS Code extension samples are TypeScript.

Node 20 LTS — current LTS, supported by VS Code's extension host.
npm — default package manager for the VS Code extension scaffold.
esbuild — fast bundler; the standard VS Code extension scaffold includes it.

Key dependencies

Package Purpose
@types/vscode VS Code API type definitions — required for all extensions
vitest Unit/service test runner — fast, TypeScript-native, no config overhead
@vscode/test-electron Runs integration tests inside a real VS Code process for participant tests
@vscode/vsce Packages the extension into a .vsix file for installation

src/extension.ts    ← skeleton: activate(), registers participant + commands
src/jira/IJiraClient.ts ← interface definition (the testing seam)

CLAUDE.md — why it matters for this project

Since the goal is for an AI agent to write and test the plugin without a real Jira instance, CLAUDE.md is critical. It tells the agent:

• What this project is and what it does
• The three-layer architecture and what belongs in each layer
• That IJiraClient is the test seam — never bypass it
• How to run unit tests (npm test) and build (npm run compile)
• That fixtures live in src/test/fixtures/ and match real Jira v10 API shapes
• Jira REST API v3 base path: /rest/api/3/
• How PAT auth works: Authorization: Bearer <token> header
