Design — Testing Strategy

How we test everything without a real Jira instance

The key insight: IJiraClient as the test seam

Production:  TicketService receives a real JiraApiClient → makes HTTP calls to your Jira
Tests:       TicketService receives a MockJiraClient → returns fixture JSON from files

The TicketService code is identical in both cases. It never knows which client it has.

What gets tested at each layer

Layer What is tested How
branchParser Regex correctly extracts ticket IDs from branch names; handles edge cases (no ticket, multiple IDs, non-standard formats) Plain unit tests — no mocks needed, pure function
TicketService Business logic: field validation, comment formatting, JQL construction, required-field checking, error handling for bad ticket IDs MockJiraClient returns fixture JSON; tests assert on service outputs
JiraApiClient Correct URL construction, auth header presence, HTTP error mapping (401 → clear message, 404 → ticket not found) Intercept fetch with a test double; no real network needed
JiraParticipant Intent parsing, ticket ID extraction from message, fallback to branch detection, error presentation in chat VS Code extension test harness (@vscode/test-electron); mock the LM API responses

Fixture files

src/test/fixtures/
  ticket-PROJ-123.json    ← realistic Jira issue response
  ticket-missing.json     ← 404 error response
  transitions-PROJ-123.json ← available status transitions (Phase 2)
  search-results.json     ← JQL search response with multiple issues

Fixtures are real Jira API response shapes — captured once from the actual API docs (or your instance), then used forever in tests. When the Jira API changes, you update the fixture, not the tests.

Test tooling

Vitest — unit tests for TicketService, branchParser, JiraApiClient (fast, no VS Code needed)
@vscode/test-electron — integration tests for JiraParticipant inside a real VS Code instance
TypeScript strict mode — catches interface mismatches between real and mock clients at compile time
