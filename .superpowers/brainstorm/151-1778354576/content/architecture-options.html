How should the extension be structured internally?

Three approaches — same user-facing behaviour, very different internal shapes

A

Monolithic handler

One large function receives every @jira message and handles everything: parse intent, call Jira, format reply.

participant.onMessage → [parse + fetch + format + respond]
  • Fast to start, minimal boilerplate
  • Becomes hard to test and extend very quickly
  • Hard to mock Jira calls without touching the whole function
B

VS Code Commands as operations

Each operation (getTicket, updateField, addComment) is a registered VS Code command. The participant parses intent and dispatches to the right command.

participant.onMessage → commands.executeCommand("jira.getTicket", …)
  • Operations are individually triggerable from the command palette — useful for debugging
  • Commands are VS Code's first-class unit — tooling support is good
  • Business logic still tangled with VS Code API
C

Service layer — clean separation (Recommended)

Three distinct layers: the participant handles conversation; services contain business logic; a Jira client handles HTTP. Each layer is testable in isolation.

JiraParticipant
understands chat → TicketService
business logic → JiraApiClient
HTTP + auth
  • JiraApiClient can be swapped for a mock in tests — no real Jira needed
  • TicketService logic is testable with plain unit tests
  • Each layer has one job — easy to extend without breaking others
  • Slightly more upfront structure, but pays back immediately in testability

My recommendation: C.
You specifically asked for testing without a real Jira instance. That requires the HTTP layer to be injectable/swappable — which only Option C makes easy. The extra structure is minimal in TypeScript and immediately pays off.
