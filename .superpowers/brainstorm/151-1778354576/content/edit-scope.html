What does "editing" a ticket mean in this MVP?

"Read" and "comment" are clear. "Edit" can mean very different things — this shapes how much Jira API surface we need to cover.

A

Status transitions only

Move a ticket through its workflow — e.g. "move PROJ-123 to In Review" or "close this ticket".

  • Very common, high-value use case
  • Jira transitions API is a separate endpoint — needs extra handling
  • Focused scope, easier to test without a real Jira instance
B

Field updates (no status)

Change standard fields like summary, description, priority, assignee, story points, fix version.

  • Uses the simpler PUT /issue endpoint
  • Good for keeping ticket data accurate while working
  • Field names and types vary per Jira project configuration
C

Both — fields + status transitions

Full editing: change any standard field and move the ticket through the workflow.

  • Most useful end state
  • More API surface to cover in MVP
  • Status transitions and field updates use different Jira endpoints

My recommendation: C — both, but phased.
Define both in the spec now so the architecture accommodates them, but implement status transitions first (higher daily value) and field edits second. This way the MVP is useful immediately and we don't paint ourselves into a corner.
