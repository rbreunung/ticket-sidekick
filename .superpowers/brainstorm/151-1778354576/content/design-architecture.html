Design — Architecture

Three layers, each with one job. Review and let me know if anything looks off.

Full data flow — @jira comment "Looks good" on PROJ-123
1. JiraParticipant Receives the chat message. Calls the VS Code Language Model API to interpret intent — determines operation is addComment, target is PROJ-123 (or falls back to branch detection), body is "Looks good".
2. TicketService Business logic. Validates inputs, orchestrates multi-step operations (e.g. fetch then update), formats results for chat output. Has no knowledge of HTTP or VS Code UI.
3. JiraApiClient Pure HTTP layer. One method per Jira REST endpoint. Handles auth headers (Personal Access Token), base URL, error codes. Defined behind an interface so tests can swap it for a mock.
4. ConfigService Reads Jira base URL from VS Code workspace settings. Reads PAT from VS Code SecretStorage (OS-level encryption — never in settings.json). Exposes a command Jira Copilot: Configure to guide first-time setup.

Project file structure

src/
  extension.ts          ← entry point, registers participant + commands
  participant/
    JiraParticipant.ts  ← chat handler, intent parsing via LM API
  services/
    TicketService.ts    ← read, edit fields, comment, (later) transitions
    ConfigService.ts    ← URL from settings, PAT from SecretStorage
  jira/
    JiraApiClient.ts    ← real HTTP client (fetch + PAT header)
    IJiraClient.ts     ← interface shared by real + mock clients
  utils/
    branchParser.ts     ← regex: extract ticket ID from git branch name
src/test/
  TicketService.test.ts
  branchParser.test.ts
  mocks/
    MockJiraClient.ts   ← implements IJiraClient, returns fixtures
