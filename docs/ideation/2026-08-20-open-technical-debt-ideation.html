Codebase Context

Ticket Sidekick is a VS Code extension with two independent GitHub Copilot Chat participants (@jira, @bitbucket) sharing ConfigService but otherwise fully separated, in a strict three-layer architecture (Participant → Service → Client interface). It already externalizes a lot of debt-tracking signal in structured prose: CLAUDE.md carries explicit "Known limitation" subsections for the Veracode and Waltz report importers, docs/solutions/ captures durable bug write-ups with YAML frontmatter, and plan docs sometimes leave an "open question" or "Scope Boundaries" note when a plan shipped narrower than originally scoped.

Two implementation-ready-but-unmerged plans sit on the current branch: a report-importer consolidation plan and a Jira-wiki render-safety hardening plan. The latter turned out to already settle two of this run's most-argued-for ideas — see the rejection summary below.

Three docs/solutions/ entries recur across almost every frame's ideas: the Waltz .xlsx unzip-compat bug (fixed by swapping to exceljs, but its root cause — a same-ecosystem fixture-generation blind spot — remains open), the Jira-wiki-markup injection bug (fixed for report importers only; email import and content preview are still exposed), and a diagnostic-log redaction false-positive (fixed, but caught only by a whole-branch review, not by tests). Each is a case where a documented "known limitation" or a narrow fix didn't generalize to the rest of the codebase — the pattern this ideation run kept converging on.

External research (Radius project, Mark Heath's technical-debt-register writeup, Stepsize's backlog-grooming guide) converges on: close won't-fix items with rationale recorded at closure time; tag debt in the same tracker as features/bugs rather than a separate ledger; run short, regular revisit passes rather than one-time documentation. A written-once "out of scope" note with no revisit trigger functionally decays into silent scope creep tolerance — which maps directly onto this repo's current state.

1

Known-limitation register with enforced revisit triggers

debt-visibility-process Confidence 90% Complexity Medium
Description

Every "Known limitation" note in CLAUDE.md and every plan's "Scope Boundaries"/"Outside this work" section currently lives as static prose with no tracker link, no TODO/FIXME pointer, no automated checklist, and no periodic review schedule. Add a lightweight, machine-checkable register — a revisit-by: field per known-limitation entry, checked by a CI step or the repo's existing ce-compound-refresh skill, or at minimum a release-checklist scan — so a documented gap gets a scheduled decision point instead of sitting indefinitely.

Basis
direct: spot-checked across CLAUDE.md, docs/plans/, and docs/solutions/ — no GitHub issue links, no TODO/FIXME comments tying code to the "Known limitation" prose, no cross-reference between a CLAUDE.md limitation and the plan doc that originated it. The Waltz unzip-compat write-up is a concrete case of a limitation that was already known and written down, then went unaddressed until a real user hit it in production — the failure was in revisiting, not in the initial decision to defer. external: Radius project's triage process (won't-fix rationale recorded at closure, monthly deep review of stale issues); Mark Heath's technical-debt-register practice (tag debt in the existing tracker, check it before touching that code area again); Stepsize's short regular grooming passes.
Rationale

This is the single highest-convergence idea across the whole run — every one of the five ideation frames independently proposed some version of it. It's also the one move that touches every current and future known-limitation entry at once, rather than closing one instance. The Waltz bug shows the concrete failure mode this closes: a correctly-documented, correctly-flagged limitation with no mechanism forcing anyone back to it.

Downsides

A register with no real enforcement repeats the exact failure it's meant to fix — the mechanism (CI check vs. ce-compound-refresh integration vs. release-checklist scan) has to actually run and actually block or nag, or it becomes one more artifact that goes stale. Idea 14 in the rejection summary below argues a genuinely different philosophy for a solo maintainer — worth a deliberate choice, not a default.

2

Non-same-author sentinel fixture policy for binary-format parsers

parsing-robustness-limits Confidence 88% Complexity Medium
Description

Every .xlsx fixture in the repo is generated by write-excel-file — scripts/fixtures/build-waltz-report-fixture.mjs:3 — the sibling package, from the same author, of the exact read-excel-file reader that was just removed for choking on real-world files. Require at least one fixture per binary-format parser (Waltz .xlsx today; any future format) produced by a structurally independent writer — a different library entirely, or a captured/anonymized real export — documented as a standing testing-policy rule, not a one-off fix.

Basis
direct: docs/solutions/integration-issues/waltz-oss-report-unzip-failure-on-real-world-xlsx.md's own Prevention section: "the fixture-generation blind spot is structural and remains open… a writer and reader from the same small ecosystem will always agree on ZIP layout by construction, so this class of bug cannot be caught by this repo's own fixtures no matter which parsing library is used downstream" — confirmed against the live import in the fixture script.
Rationale

This is the root cause of the exact bug the current branch (fix/waltz-oss-report-unzip-compat) exists to fix — the reader changed, the thing that let the bug hide from CI did not. Four independent ideation frames converged on this same conclusion from four different angles (pain, inversion, leverage, cross-domain analogy), which is a strong signal the gap is real and not an artifact of one frame's bias.

Downsides

Requires actually obtaining an independently-produced .xlsx — a different toolchain export, or a real anonymized customer file — which is acquisition effort, not code. It also doesn't close the class permanently: the next distinct producer variant (a different Waltz version, a different locale) can still surprise a two-fixture suite. It raises the bar; it doesn't make the bar unliftable.

3

Replace the parse-timeout race with real cancellation

parsing-robustness-limits Confidence 85% Complexity Medium
Description

src/utils/waltzReport.ts:220's PARSE_TIMEOUT_MS is a Promise.race against a 15s timer — it stops the caller from waiting, but the parse itself keeps running and consuming CPU/memory afterward. Two-stage move: (1) cheap first step — log a diagnostic line (via the existing onDiag/logDiag pattern already used throughout the codebase) at the timeout-rejection branch, so it's finally observable whether this has ever actually fired for a real user; (2) the real fix — move the parse into a Node worker_thread that can be genuinely .terminate()d on timeout.

Basis
direct: the code and its own comment at waltzReport.ts:220-224: "hard ceiling so a pathological file … fails fast instead of exhausting memory or hanging the extension host. Bounds wall-clock time, not memory directly…" — and CLAUDE.md's matching admission: "it does not itself prevent resource exhaustion." The gap is self-documented, not inferred.
Rationale

Four frames converged on closing this gap (inversion, cross-domain analogy, constraint-flipping, pain/friction's instrumentation angle) — this is a named, security-adjacent resource-exhaustion vector on a file-import path whose own threat model explicitly names "decompression-bomb-style" files. Nobody currently knows whether it has ever fired for a real user; the diagnostic step answers that cheaply before committing to the bigger refactor.

Downsides

The worker_thread refactor changes the parse entry point's data marshalling — results have to cross the thread boundary via structured clone, which is a real (if contained) code change to a function that currently returns rich in-process objects. The diagnostic-logging step is nearly free; the full fix is a genuine chunk of work with its own test burden, and is worth sequencing as its own decision once the instrumentation shows whether it's needed.

4

Automate the render-safety plan's deferred manual verification

injection-sanitization-gaps Confidence 85% Complexity Low
Description

The unmerged render-safety plan explicitly defers, as a manual, non-blocking, non-automatable check, whether Jira's own renderer re-interprets wiki-markup trigger sequences inside {{monospace}}/{code}/{noformat} macros — the exact class of injection the plan exists to close. Write a small integration script: post a probe ticket with each trigger sequence wrapped in each macro to a real or sandbox Jira instance, read it back via the API, and diff the rendered result — instead of leaving this as an indefinitely-deferred manual step.

Basis
direct: the plan's own text, verbatim: "Assumes Jira's own renderer does not re-interpret wiki-markup trigger sequences inside its {{monospace}}/{code}/{noformat} macros. Unverified against a live instance; see KTD3 and the Verification Contract's deferred manual check" and, in the Verification Contract: "Deferred, non-blocking: a one-time manual confirmation… This cannot be automated from this repo and does not block merge."
Rationale

This is the load-bearing assumption behind the whole render-safety fix. If it's wrong, the macro-wrapping defense the plan's converter design relies on doesn't actually neutralize the trigger inside those macros — and under the plan's current scope, nobody would find out until someone hits it, the same failure shape as the Waltz bug above.

Downsides

Needs a real or sandbox Jira instance and credentials reachable from wherever the script runs — it can't be exercised inside this repo's own CI without one. If no such instance is easily available, a well-scheduled one-time manual check (tied to idea 1's revisit-trigger mechanism, rather than left open-ended) may be the more realistic near-term version of this idea.

Sibling-parity audit between @jira and @bitbucket

ai-ux-backlog Confidence 82% Complexity Medium
Description

@bitbucket already resolves a token budget from modelContextTokens → request.model.maxInputTokens → a 60 000 fallback, multiplied by contextBudgetRatio (default 0.7) — BitbucketParticipant.ts:470-474 (and again at 573-577). @jira's equivalent context-assembly path has no cap at all. Concretely: lift Bitbucket's existing logic into a shared src/utils/tokenBudget.ts both participants use. As a process rule: when a reliability/UX hardening fix lands on one participant, require an explicit "applies to the sibling, or explicitly doesn't, because X" note before the task counts as done — closing this gap and preventing the next one like it.

Basis
direct: BitbucketParticipant.ts:470-474 confirmed as cited; src/participant/jira/contentHandler.ts's buildContentContext() confirmed to have no equivalent cap. Separately, all 5 proposals in docs/bitbucket-follow-up-improvements.md are already delivered, while several parallel proposals in docs/ai-usecases-review.md for @jira — including token budgeting and sturdier refusal detection — remain open.
Rationale

The fix already exists and already works in the codebase, under a different participant — the leverage move is relocating proven logic, not designing something new. It also names a real process gap: two structurally parallel features are drifting because nothing currently checks whether a fix on one side should apply to the other.

Downsides

Extracting the shared utility touches Bitbucket's already-working, already-tested code path too — real if modest regression risk on a feature that currently works. The process half (the parity checklist) only has value if it's actually followed; a rule nobody enforces is no better than the status quo.

6

Unify report-importer and cleanup review-table rendering

importer-architecture-debt Confidence 70% Complexity Medium
Description

Report importers use toggle semantics (reply with ids to flip inclusion); cleanupHandler.ts's bulk-transition review uses skip semantics (default-all-included, reply with ids to exclude) — two structurally separate table implementations. The consolidation plan's own Scope Boundaries call this "a real interaction-model difference a future unification will need to reconcile, not just a wording difference" and deliberately park it. Rather than a big-bang UX merge, extract just the shared table-rendering primitives (borders, column truncation, "New"/"Already ticketed" framing) now, leaving the toggle-vs-skip parsing semantics genuinely separate.

Basis
direct: verified the semantics directly — cleanup's review parsing returns a one-way {action:'skip', keys}, report review's returns a bidirectional {action:'toggle', ids} with included: !r.included — a real, not cosmetic, difference, confirmed against the consolidation plan's own Scope Boundaries text.
Rationale

Every future bulk-action feature currently means writing another bespoke review-table-plus-parser instead of extending one — the render layer is genuinely duplicated (dossier cites sessionState.ts:92-115 for cleanup and 519-583 for reports) even though the plan's own authors correctly judged the semantic merge itself as a separate, deferrable decision.

Downsides

Even the render-only slice touches two working, already-hardened flows — this exact area of the codebase has produced three of the repo's documented docs/solutions/ bugs. The plan's authors already judged full unification deferrable; the render-only slice is a smaller, safer bite, but timing it against other priorities (especially idea 1's process fix and idea 4's security-plan gap) is a real sequencing question, not a given.
