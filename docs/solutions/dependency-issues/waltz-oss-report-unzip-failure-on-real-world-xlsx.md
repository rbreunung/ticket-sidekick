# read-excel-file/unzipper-esm fails to unzip real-world .xlsx exports that open fine in Excel

## Problem

`parseWaltzReport()` (`src/utils/waltzReport.ts`) used `read-excel-file/node`'s `readSheet()` to parse the Waltz OSS report `.xlsx`. Its Node backend is hardcoded (not exposed as a configurable option) to `unzipper-esm` — a sequential/streaming ZIP reader that walks local file headers in order and trusts each one's declared entry size. A real-world `.xlsx` exported by Waltz (or, generally, by any tool using a streaming XLSX writer, e.g. Java's Apache POI `SXSSFWorkbook`) can legally defer an entry's size to a trailing data descriptor instead of writing it in the local header (ZIP spec general-purpose flag bit 3). Excel's own OOXML reader — and any zip reader that resolves entries via the End-Of-Central-Directory record first — handles this fine. `unzipper-esm` does not: it throws a ZIP parse error (`INVALID_SIGNATURE`/`FILE_ENDED` internally, surfaced by `read-excel-file` as `INVALID_ZIP` → `Couldn't unzip \`.xlsx\` file contents`) partway through such a file.

## Symptoms

A user runs **Ticket Sidekick: Create Jira tickets from OSS report (.xlsx)** (or `@jira import oss report`) against a genuinely valid, non-corrupted, non-password-protected Waltz export and gets:

```
Could not read OSS report: Couldn't unzip `.xlsx` file contents
```

Confirmed via user-reported diagnostics: the file opens cleanly in Excel with no password prompt or repair warning (rules out encrypted/legacy-`.xls` files — those are caught earlier by a distinct, clearer error via `read-excel-file`'s leading-byte OLE2/CFB signature check, `D0 CF 11 E0`) and lives in a plain local folder with no cloud-sync involvement (rules out a truncated/placeholder download). This was also the very first time this feature had been exercised against a real report — every existing `waltzReport.test.ts` fixture is generated by `scripts/fixtures/build-waltz-report-fixture.mjs` via `write-excel-file`, the *same author's* sibling package to `read-excel-file`. A writer and reader from the same small ecosystem always agree on ZIP layout, so this class of real-world producer incompatibility was structurally untestable with the existing fixtures — CI stayed green while real users hit the bug.

## Root Cause

`unpackXlsxFileNode.js` in `read-excel-file`'s Node build pipes the input buffer through `unzipFromStream.js`, which is hardcoded to `unzipFromStream.unzipper.js` (the `unzipper-esm` backend) — there is no public option on `readSheet()`/`readXlsxFile()` to select the library's alternate `fflate`-based backend for the Node path. `unzipper-esm`'s `Parse()` stream (`lib/parse.js`) reads local file header signatures sequentially and throws `INVALID_SIGNATURE`/`FILE_ENDED` when the stream position doesn't land on the next expected header — exactly what happens when it walks past a data-descriptor-style entry it doesn't correctly skip. This is converted to `UnzipError` → `InvalidInputError('INVALID_ZIP', …)`, whose fixed message is `Couldn't unzip \`.xlsx\` file contents` (`read-excel-file/commonjs/xlsx/file/InvalidInputError.js`).

## What Fixed It

Swapped the sheet-reading layer in `src/utils/waltzReport.ts` from `read-excel-file/node` to `exceljs`'s `workbook.xlsx.load(buffer)`. `exceljs`'s `load()` method reads the archive via `jszip.loadAsync()`, which locates entries through the ZIP's End-Of-Central-Directory record — the same central-directory-first strategy Excel's own OOXML reader uses — rather than scanning local file headers sequentially. Central-directory-first parsing doesn't depend on a local header's declared size at all, so it isn't tripped by deferred-size/data-descriptor entries.

Implementation notes:
- `readNamedSheet()`/`readOptionalNamedSheet()` were rewritten to operate on an already-loaded `ExcelJS.Workbook` (via a new `loadWaltzWorkbook()` that unzips once, up front) instead of re-reading the raw buffer per sheet — a minor efficiency win alongside the compatibility fix, since the old per-sheet `readSheet(buffer, sheetName)` calls re-unzipped the whole archive three times.
- `read-excel-file`'s `Schema<T>`/`SheetNotFoundError` types were re-implemented locally (same shape, same call sites) since `exceljs` gives raw cells, not schema-validated rows — kept intentionally minimal (just column-header lookup + required/type validation) to preserve the existing error-message contracts (`OSS report sheet "..." has invalid rows: ...`, `OSS report is missing the required "ComponentRemediations" sheet. (...)`) that `waltzReport.test.ts` already asserts on.
- `exceljs`'s bundled `index.d.ts` globally re-declares `interface Buffer extends ArrayBuffer {}`, which conflicts with `@types/node`'s modern generic `Buffer<TArrayBuffer>` and makes the `workbook.xlsx.load()` call's `buffer` argument fail structural type-checking even though it's a real Node `Buffer` at runtime. Routed around with a single, commented `as any` at that one call site — a stale-vendored-typings issue, not a runtime safety concern.
- `read-excel-file`/`write-excel-file` were considered as a pair, but only `read-excel-file` was removed — `write-excel-file` still generates the test fixtures and has no unzip involved (it's a writer).

## Verification

All 26 existing `waltzReport.test.ts` tests — including the malformed-file and missing-required-sheet error-message assertions — passed unchanged against the new implementation, confirming full behavioral parity for every previously-tested path. `npm run compile` and the full 962-test suite are green. **Not independently verified**: no reproduction of the actual failing file was available during this fix (the user could not share it), so the exact byte-level ZIP feature (data-descriptor entries) is the best-evidenced theory from `unzipper-esm`'s own error taxonomy and the ruled-out alternatives, not a confirmed-by-reproduction fact. The user was asked to confirm against their real file after the fix ships.

## Prevention

The structural gap — every Waltz fixture generated by the same author's sibling writer library, so a real-world producer incompatibility can never surface in CI — is not closed by this fix. A future schema or format change from Waltz (or any other real export source) could reintroduce a similar "works in tests, fails for real users" gap. Building a genuinely representative fixture (e.g. one hand-constructed with streaming/data-descriptor ZIP entries) was considered and deliberately deferred: it would encode an unconfirmed theory about the exact byte-level trigger as if it were proven, which risks false confidence more than it adds real coverage. If this class of bug recurs, obtaining the actual failing file before attempting a fix (rather than reasoning from library internals alone) is the more reliable path.
