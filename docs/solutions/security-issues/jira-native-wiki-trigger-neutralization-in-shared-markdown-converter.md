# Raw Jira-Native Wiki-Markup Triggers Bypass markdownToJiraWiki() Itself, Not Just the Report Importers

## Problem

`markdownToJiraWiki()` (`src/utils/markdownToJiraWiki.ts`) is the single converter every Jira-content-generating flow in this extension shares — content preview/refinement, email-to-ticket, and the Veracode/Waltz report importers all funnel through it. It could not guarantee that a raw, unconverted Jira-native wiki-markup trigger sequence embedded in untrusted input text (an email body, or LLM-generated comment/description content) would never survive unmodified into the string sent to Jira. The concrete, named exploit: a raw `!http://attacker.example/tracker.gif!` (Jira-native remote-image-embed syntax) typed into an email or generated by an LLM would reach a created or updated ticket unchanged and render as a live, auto-loading tracking pixel — leaking viewer IP/user-agent/view-timing to the attacker with zero user interaction, on every view of the ticket. Two further gaps existed entirely *outside* the converter, so no amount of converter hardening alone could have closed them: `emailHandler.ts`'s `buildEmailJiraWiki()` reconstructs literal Jira image-embed syntax (`!name|thumbnail!`) directly from an attacker-controlled (email-derived) attachment filename, and `buildEmailCommentHeader()` interpolates the attacker-controlled email `From` display name directly into a live Jira comment line (`*From:* ${senderName}`) — neither value passes through the converter at all.

Fix implemented in [PR #38](https://github.com/rbreunung/ticket-sidekick/pull/38), merged to `main` 2026-08-24, branch `fix/jira-wiki-render-safety`, per `docs/plans/2026-08-14-001-fix-jira-wiki-render-safety-plan.md`. The plan was drafted 2026-08-13/14 (session history — see "What Didn't Work" below) and implemented ten days later, also on 2026-08-24.

## Symptoms

- A CVE summary, LLM-generated ticket description, or a raw email body containing `!http://attacker.example/t.gif!` would previously pass through `markdownToJiraWiki()`'s `inline()` fallback unchanged — the converter only recognizes *Markdown* syntax and passes anything else straight through — and land in the created/updated ticket as a working tracking pixel.
- Same failure shape for four more Jira-native trigger sequences the converter had no awareness of at all: `-text-` (strikethrough), `+text+` (underline), `^text^` (superscript), `??text??` (citation), and `{quote}`/`{color}`/`{panel}`/`{noformat}` macro block delimiters.
- A subtler variant: the converter's *own legitimate* Markdown-to-Jira conversion produces exactly these same shapes as its correct output — `~~real~~` → `-real-` for strikethrough, `![img](url)` → `!url!` for images. Before the fix there was no way to tell the converter's own generated `-real-`/`!url!` apart from a same-shape string an attacker typed raw on the same line; both were byte-identical strings sitting in the same buffer.
- Independently of the converter: an email attachment filename containing `!` or `|` (e.g. `evil!.gif`, `report|malicious.pdf`) reconstructed into `buildEmailJiraWiki()`'s `!name|thumbnail!` template would inject a second live delimiter — either a second `!url!` embed trigger, or an extra `|` letting the attacker append/alter Jira image attributes (align, border, etc.). An email `From` display name containing `{color}`/`!`/etc. (e.g. `Evil{color}HACKED{color}!`) interpolated into `buildEmailCommentHeader()`'s `*From:* ${senderName}` line would inject live macro/image-embed markup directly into the posted comment.
- No error, crash, or test failure surfaced any of this — the only observable artifact was the rendered ticket in Jira itself, exactly the failure mode the predecessor incident already flagged.

## What Didn't Work

This is a direct continuation of `docs/solutions/security-issues/waltz-oss-report-markdown-injection-in-jira-wiki-converter.md`, whose "Related Issues" section explicitly predicted this exact gap. That prior work was not wrong — its fix (character-stripping via `sanitizeCellText()`, later extended with the Jira-native trigger set: `-+^?{}!`) was a correct, well-verified defense, but it was **scoped to the report importers only**. `sanitizeCellText()` runs on individual Veracode/Waltz field values *before* they're assembled into Markdown and handed to `markdownToJiraWiki()`. Every other caller of the converter — content preview/refinement (comments and descriptions typed or LLM-generated through `@jira`), and the two email-handler call sites that never call the converter at all — had no equivalent gate. The prior fix protected one producer of untrusted text reaching the converter; it did nothing for the converter itself or for callers that bypass it.

Two naive approaches were also explicitly rejected during planning, not attempted and reverted:

- **Blanket-stripping the trigger characters (`-+^?{}!` etc.) everywhere text passes through the converter.** This would mangle ordinary prose — every bare `-` in "co-worker" or "state-of-the-art", every `?`/`!` at the end of an ordinary sentence, every `^` in "x^2" — which the plan's R2 requirement explicitly forbade: zero regression to legitimate Markdown rendering of normal email/LLM text.
- **A naive shape-match regex like `/-(.+?)-/` applied directly to raw text.** This would incorrectly treat the hyphen *between* two segments of a hyphenated compound word as a delimiter pair — e.g. matching `-of-` inside "state-of-the-art" — turning ordinary prose into (incorrectly) neutralized garbage, still without actually being scoped tightly enough to be safe.

**The planning process itself took several wrong turns before landing on the shipped design (session history):**

- The first framing proposed during brainstorming was a "reusable two-sink sanitization pattern" — a checklist, lint rule, or test-requirement enforcement mechanism rather than an actual code fix. The user rejected this as too abstract: "I didn't understand it. What will we do to prevent the issue materializing?" — redirecting toward a concrete code-level fix instead of a process artifact.
- The scope was initially framed too narrowly, around the report importers alone. The user then pointed out that `markdownToJiraWiki()` is the single shared chokepoint used by *every* Jira-content flow — single-ticket create/edit, comments, and `.eml`-to-ticket import, not just Veracode/Waltz. Verifying this against source confirmed it was correct and more serious than first scoped: `buildEmailJiraWiki()` in `emailHandler.ts` piped email body text into `markdownToJiraWiki()` with **zero** sanitization at the time — any inbound email could already plant a live tracking pixel.
- Three design approaches of increasing invasiveness were laid out once the real scope was clear (patch each call site individually / add an opt-in sanitizer utility callers must remember to invoke / harden the shared converter itself). The user picked hardening the converter at its one chokepoint, which is what shipped as KTD1's "fix at the shared chokepoint, not at each call site" decision.
- An earlier design (what became KTD7 in an intermediate draft) tried a "trusted prefix character" to block line-start injection. Doc review's security-lens caught that this didn't actually work: Jira's line-start markup regexes (headings, lists, quotes) trim leading whitespace before matching, so a prefixed line could still be re-interpreted as a live trigger under certain conditions. This forced the redesign that became KTD3's unconditional `{`/`}` stripping for cross-line macro splits — a structurally different fix, not a patched version of the prefix idea.
- KTD1's own first draft dropped `!text!` — the plan's own headline exploit, the exact case named in the Problem Frame — from its neutralization shape list. This gap was independently caught by 3 of 4 doc-review personas (security, feasibility, and adversarial lenses all flagged it separately, a strong convergent-evidence signal) before implementation began, and fixed by explicitly adding `!text!` back to KTD1's shape list.

## Solution

### 1. Shape-aware, word-boundary-gated neutralization (`src/utils/markdownToJiraWiki.ts:105-146`)

Five Jira-native trigger shapes are defined and matched only when actually wrapped at a word boundary — not a blanket character strip:

```ts
// src/utils/markdownToJiraWiki.ts
const JIRA_TRIGGER_SHAPES: ReadonlyArray<{ delimiter: string; char: string }> = [
  { delimiter: '??', char: '?' }, // citation — checked first so its two '?' aren't seen as loose '?' noise
  { delimiter: '-', char: '-' },  // strikethrough
  { delimiter: '+', char: '+' },  // underline
  { delimiter: '^', char: '^' },  // superscript
  { delimiter: '!', char: '!' },  // remote image embed
];

function buildWrapPattern(delimiter: string, char: string): RegExp {
  const d = escapeRegExp(delimiter);
  const c = escapeRegExp(char);
  // (?<!\w) / (?!\w)   — delimiters sit at a word boundary, not inside a run of word characters
  // (?!\s) / (?<!\s)   — content may not start or end with whitespace
  // [^${c}\n]+?        — content excludes the delimiter's own character and newlines, non-greedy
  return new RegExp(`(?<!\\w)${d}(?!\\s)([^${c}\\n]+?)(?<!\\s)${d}(?!\\w)`, 'g');
}
```

`neutralizeJiraTriggers()` runs each pattern and simply replaces the matched span with its inner content (stripping the delimiters, leaving the text otherwise intact):

```ts
function neutralizeJiraTriggers(text: string): string {
  for (const pattern of WRAP_PATTERNS) {
    text = text.replace(pattern, (_match, content: string) => content);
  }
  text = text.replace(/[{}]/g, ''); // unconditional — see mechanism 3 below
  return text;
}
```

The word-boundary lookaround (`(?<!\w)`/`(?!\w)`) is what closes the compound-word false-positive class the naive approach fell into: in "state-of-the-art", every hyphen has a letter on both sides, so none of them ever qualifies as an opening *or* closing delimiter — the regex simply never fires there. Verified directly by test: `markdownToJiraWiki('a state-of-the-art solution')` returns the string completely unchanged (`src/test/markdownToJiraWiki.test.ts:210-213`), and ordinary prose like `'my co-worker computed x^2 today'` and `'what? really great!'` are likewise left untouched (`:205-208`).

### 2. Array-indexed extraction for image/strikethrough output (`src/utils/markdownToJiraWiki.ts:186-220`)

Before this fix, the converter's own legitimate strikethrough conversion re-embedded content directly in the string: `text.replace(/~~(.+?)~~/g, '-$1-')`. After conversion, a legitimate `-real-` (converted from `~~real~~`) is a byte-identical string to a raw `-fake-` an attacker typed directly on the same line — nothing left in the buffer distinguishes them, so `neutralizeJiraTriggers()` (which must strip the raw one) would necessarily also strip the legitimate one.

The fix extracts both image and strikethrough output out-of-band into an array, mirroring the code-span pattern the file already used, and restores them only *after* trigger neutralization runs:

```ts
// Before (spoofable — content re-embedded live in the string):
text = text.replace(/~~(.+?)~~/g, '-$1-');

// After (src/utils/markdownToJiraWiki.ts) — array-indexed, unspoofable:
const strikeSpans: string[] = [];
text = text.replace(/~~(.+?)~~/g, (_, content) => {
  strikeSpans.push(`-${content}-`);
  return `\x00S${strikeSpans.length - 1}\x00`;
});

// ... neutralizeJiraTriggers(text) runs here, only ever seeing raw attacker-typed
//     -text-/!text! sequences, since legitimate output is now an opaque \x00S<n>\x00 token ...

// Restore strikethrough only after neutralization:
text = text.replace(/\x00S(\d+)\x00/g, (_, idx) => strikeSpans[parseInt(idx, 10)]);
```

Images follow the identical `\x00I<n>\x00` pattern. Because the placeholder token (`\x00S0\x00`) contains a null byte and a letter/digit sequence no attacker-controlled text can produce through the same code path, `neutralizeJiraTriggers()` can never mistake a restored token for something to neutralize, and an attacker's raw `-fake-` on the same line has no token to hide behind — it's still live text when the neutralization pass runs. Verified by test AE5: `markdownToJiraWiki('legit ~~real~~ and raw -fake- here')` produces output containing `-real-` but not `-fake-` (`src/test/markdownToJiraWiki.test.ts:186-193`).

### 3. Unconditional `{`/`}` stripping for cross-line macro splits (`src/utils/markdownToJiraWiki.ts:146`)

`inline()` is called once per line (or per blockquote-line, or per table cell) — the converter's line-router never assembles the full multi-line document before calling it. So a `{quote}`/`{color}`/`{panel}` macro's opening half could sit on one line and its closing half on a later line; no single `inline()` call ever sees both halves together, so pair-matching within one call structurally cannot detect the split. The fix strips every raw `{`/`}` unconditionally, regardless of pairing:

```ts
text = text.replace(/[{}]/g, '');
```

Accepted trade-off, noted directly in the source comment: a legitimate footnote-style `{1}` in ordinary prose also loses its braces — there's no way to distinguish that from an attacker-split macro half within a single line/cell. Verified: `markdownToJiraWiki('intro {quote}\nhidden malicious content\n{quote} outro')` does not contain `{quote}` in the output (`src/test/markdownToJiraWiki.test.ts:180-184`), and the prose trade-off is captured directly too — `markdownToJiraWiki('see note {1} above')` returns `'see note 1 above'` (`:175-178`).

### 4. Single source of truth for the trigger character set

`markdownToJiraWiki.ts` now exports `TRIGGER_CHARS` / `TRIGGER_CHARS_PATTERN` (the full union of the Markdown-defeating set and the Jira-native set: `` *_`[]~-+^?{}! ``). `src/utils/reportImport.ts:10,197` imports `TRIGGER_CHARS_PATTERN` from there and uses it in `sanitizeCellText()` instead of its own previously-inline character-class literal:

```ts
// src/utils/reportImport.ts
import { TRIGGER_CHARS_PATTERN } from './markdownToJiraWiki';
// ...
export function sanitizeCellText(value: string): string {
  return value
    .replace(/\r\n|\r|\n/g, ' ')
    .replace(/\|/g, '/')
    .replace(TRIGGER_CHARS_PATTERN, '');
}
```

Behavior is byte-identical to the prior inline literal — this is a refactor for maintainability (one list to keep exhaustive instead of two independently-maintained ones), not a behavior change. Both layers stay: the converter-level fix guarantees render safety for every caller; the report importers' field-level sanitizer still separately protects against a value breaking out of its slot in a hand-assembled Markdown template. Neither replaces the other.

### 5. Closing the two converter-external gaps with the existing sanitizer (`src/participant/jira/emailHandler.ts`)

`buildEmailJiraWiki()`'s attachment-filename reconstruction and `buildEmailCommentHeader()`'s sender-name interpolation both build live Jira wiki markup directly, never passing through `markdownToJiraWiki()`. No new sanitization logic was written — `sanitizeCellText()` (already existed, already used by the report importers) is applied to just the captured untrusted value, never to the whole template string:

```ts
// Before
return jiraWiki.replace(/\[📎 ([^\]]+)\]/g, '!$1|thumbnail!');
// After — only the captured name is sanitized; the template's own "!"/"|" delimiters survive
return jiraWiki.replace(/\[📎 ([^\]]+)\]/g, (_match, name: string) => `!${sanitizeCellText(name)}|thumbnail!`);

// Before
if (senderName) parts.push(`*From:* ${senderName}`);
// After — only the captured name is sanitized; the template's own "*" bold markers survive
if (senderName) parts.push(`*From:* ${sanitizeCellText(senderName)}`);
```

Sanitizing the value alone (not the surrounding template) is the deliberate, load-bearing detail — sanitizing the whole template string would strip its own intentional `!`/`|`/`*` delimiter characters and break the feature. Verified by tests in `src/test/emailHandler.test.ts:88-110` (crafted filename containing `!` produces exactly two `!` characters in the output — the template's own two delimiters, no more; crafted filename containing `|` produces exactly one `|`) and `:132-152` (crafted sender name `'Evil{color}HACKED{color}!'` produces `'*From:* EvilcolorHACKEDcolor\n\n'`, containing neither `{` nor `}`).

### 6. End-to-end regression proof

`src/test/contentHandler.test.ts:410-498` adds three integration tests that exercise the real `handleContentSession()` flow (`createTicket`, `addComment`, `updateDescription`) with a crafted payload (`'Root cause analysis: -struck- the old assumption, see !http://evil.example/t.gif! for details.'`) and assert on the text actually captured at the mocked Jira client sink — proving both `markdownToJiraWiki()` call sites in `contentHandler.ts` need no additional sanitization beyond the converter-level fix. The pre-existing Veracode/Waltz test suites required zero edits and pass byte-for-byte, confirming the converter changes don't regress the report importers' existing field-level sanitizer.

## Why This Works

The predecessor incident doc identified two root causes: the trigger character set had been "under-enumerated twice before" (Markdown characters caught, Jira-native characters missed the first time; caught later but only in the report-importer sanitizer, not the converter), and the converter "has no escape-character support at all" (so backslash-escaping approaches are structurally useless against it). This fix closes the *class* of gap rather than patching one instance, on three axes:

1. **Chokepoint, not per-caller patching.** Every caller of `markdownToJiraWiki()` — present and future — now gets the neutralization for free, because it lives inside `inline()`, the converter's own shared code path, rather than being re-implemented (or forgotten) at each call site. This directly answers the predecessor doc's own root-cause note that a denylist sanitizer applied only at the producer side "will silently stop being exhaustive again" as new consumers are added — content preview and email-to-ticket flows never needed a `sanitizeCellText()` call, because they never touched raw untrusted values the way the importers do; the vulnerability was inside the shared converter itself, unreachable by hardening any one producer.
2. **Array-indexed extraction makes "is this legitimate converter output or raw attacker text" a structurally answerable question**, not a heuristic one. Content-embedded markers (the old `-$1-` inline substitution) collapse the distinction between "the converter produced this" and "the input already looked like this" into byte-identical strings with no way to tell them apart after the fact. An out-of-band array reference can't be spoofed by input text, because the placeholder token space (`\x00S<n>\x00`) is disjoint from anything attacker text can produce through the same code path.
3. **Unconditional stripping covers what single-call pair-matching structurally cannot.** Because `inline()` is invoked per-line, no in-call logic can ever see a `{quote}`/`{quote}` pair split across two lines. The fix doesn't try to detect the split — it removes the character the split depends on, unconditionally, accepting a narrow prose cost (`{1}` footnotes) in exchange for a defense that holds regardless of how the attacker distributes the payload across lines or table cells.

## Prevention

1. **Array-indexed extraction vs. content-embedded markers is a general, reusable technique** — not a one-off fix. Whenever your own transform's legitimate output can end up byte-identical, on the same line, to a same-shape sequence an attacker could type raw in the input, a content-embedded marker (`` `$1` `` substituted back into the string) cannot be told apart from raw input after the fact. Extracting the legitimate output into an out-of-band array and replacing it with a null-byte-prefixed placeholder token (as the existing code-span handling already did, and as this fix extends to images and strikethrough) is the general pattern: restore only after any input-directed neutralization pass has already run over the (now placeholder-only) string.
2. **Word-boundary-gated regex matching is the correct guard against compound-word false positives when shape-matching wrapped delimiters** (`-text-`, `+text+`, etc.) in prose. `(?<!\w)delim(?!\s)...(?<!\s)delim(?!\w)` — delimiter at a word boundary, content not starting/ending in whitespace — closes the "matches between two hyphens inside a hyphenated word" failure mode a naive `/-(.+?)-/` falls into, without needing special-case logic for specific compound words.
3. **Any single-pass-per-line (or per-cell) converter has a structural blind spot for cross-boundary attacks** that pair-matching within one call cannot see — a payload split across lines, table cells, or any other unit the converter processes independently. When the downstream renderer treats the whole assembled document as one unit, but your converter never sees the whole document in one call, pair-matching is not a sufficient defense; unconditional stripping of the single character the pairing depends on is sometimes the only closed-form fix, and it is worth explicitly accepting the (usually small) legitimate-content cost that comes with it rather than searching for a cleverer detection scheme that doesn't exist for a per-line processing model.
4. **A single-character trusted-prefix trick is not a reliable defense against line-start markup re-interpretation** (session history) — a design considered during this plan's drafting tried prefixing untrusted lines with a fixed character to prevent Jira's line-start rules (headings, lists, quotes) from re-triggering, but those rules trim leading whitespace before matching, so the prefix didn't reliably survive. Prefer removing or neutralizing the actual trigger character over trying to out-position it.
5. **When several independent review lenses (security, feasibility, adversarial) each flag the same gap separately, treat that convergence as a strong signal**, not noise to average away — in this plan, three of four doc-review personas independently caught that the first draft's neutralization shape list omitted `!text!`, the plan's own named headline exploit. Convergent, independent findings on the same gap are worth fixing immediately rather than adjudicating away.
6. **Test scenarios worth keeping as a template for future converter-safety work:**
   - The AE5-style test: assert your own legitimate transformed output survives, *and* a same-shape raw injection on the same line does not — `markdownToJiraWiki('legit ~~real~~ and raw -fake- here')` asserting both `toContain('-real-')` and `not.toContain('-fake-')` (`src/test/markdownToJiraWiki.test.ts:186-193`).
   - The AE6-style test: confirm code spans / fenced code blocks remain fully exempt from neutralization, since they're meant to display raw text literally — `` markdownToJiraWiki('`!http://attacker.example/t.gif!`') `` should render the trigger as inert literal text inside Jira's own monospace macro, not get stripped or altered (`src/test/markdownToJiraWiki.test.ts:195-203`).
   - The cross-line macro-split test: feed a payload with an opening delimiter on one line and its closing counterpart on a later line, and assert the joined output contains neither half as a live pair (`src/test/markdownToJiraWiki.test.ts:180-184`).
   - The compound-word / bare-punctuation regression test: assert ordinary prose containing bare trigger characters (`state-of-the-art`, `x^2`, `what? really great!`) survives byte-for-byte unchanged — this is the test that would have caught the rejected naive-regex approach before it shipped (`src/test/markdownToJiraWiki.test.ts:205-213`).
