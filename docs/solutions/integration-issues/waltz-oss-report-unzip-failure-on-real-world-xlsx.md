# read-excel-file/unzipper-esm fails to unzip real-world .xlsx exports that open fine in Excel

## Problem

`parseWaltzReport()` in `src/utils/waltzReport.ts` used `read-excel-file`'s Node backend to read the Waltz OSS report `.xlsx`, and that backend fails to unzip a class of genuine, non-corrupted `.xlsx` files that Excel itself opens without complaint — breaking `@jira import oss report` / **Ticket Sidekick: Create Jira tickets from OSS report (.xlsx)** on real-world exports the first time the feature was ever exercised against one.

## Symptoms

- `@jira import oss report` (and the equivalent Command Palette command) fails with `Could not read OSS report: Couldn't unzip \`.xlsx\` file contents`.
- The same file opens cleanly in Excel — no password prompt, no repair warning.
- The file lives in a plain local (non-cloud-synced) Downloads folder.
- Every pre-existing `waltzReport.test.ts` fixture stayed green throughout — the bug was invisible to CI.

## What Didn't Work

The failing file itself could not be shared, so the investigation worked backward from the error message and forward from three targeted diagnostic questions, ruling out each plausible cause with concrete evidence rather than assumption:

- **Password-protected `.xlsx`** — ruled out. `read-excel-file`'s `InputValidationStream` sniffs the leading bytes and throws a distinct, clearer error for the OLE2/Compound-File-Binary signature (`D0 CF 11 E0`, used by both legacy `.xls` and MS-OFFCRYPTO-encrypted `.xlsx`) before ever reaching the ZIP parser. Getting the ZIP-specific `INVALID_ZIP` error instead of that CFB-signature error proves the file was not password-protected.
- **Legacy `.xls` renamed to `.xlsx`** — ruled out by the same signature check: a real `.xls` also trips the CFB path, not the ZIP path.
- **File corruption / truncated download** — ruled out by the user's own confirmation that the file opens in Excel with no repair-warning dialog, and that it lives in a plain local folder with no cloud-sync process (OneDrive/Dropbox placeholder files being a common source of truncated-looking local copies).
- **Regression** — ruled out: the user confirmed this was the first time anyone had exercised the Waltz import feature against a real report, so there was no prior working state to regress from.

With those four eliminated, the remaining explanation was a ZIP-parser compatibility gap. Tracing into `read-excel-file`'s own internals — **historical citation: `read-excel-file` was removed by this fix, so these paths no longer exist under `node_modules/` in the current tree; they're preserved here as investigation evidence, findable again by reinstalling `read-excel-file@9.3.10`** — showed the `INVALID_ZIP` error is raised when `unzipper-esm` (the package's Node ZIP backend, hardcoded in `read-excel-file`'s `export/unpackXlsxFileNode.js` with no configurable alternative) fails to parse the byte stream, per `node_modules/read-excel-file/commonjs/xlsx/file/InvalidInputError.js`. `unzipper-esm`'s own error taxonomy (`INVALID_SIGNATURE` in its `lib/parse.js`, `FILE_ENDED` in its `lib/PullStream.js`) is characteristic of a sequential ZIP reader losing sync with a stream containing deferred-size (data-descriptor) entries, a legal ZIP variant. Web research into `read-excel-file`'s CHANGELOG confirmed the library has churned between `unzipper`/`fflate`/`unzipper-esm` backends multiple times specifically over Node ZIP-parsing tradeoffs — corroborating this as a known class of weakness rather than a one-off. Finally, inspecting `scripts/fixtures/build-waltz-report-fixture.mjs` showed every test fixture is generated via `write-excel-file`, the same author's sibling writer package — meaning writer and reader had always agreed on ZIP layout in every test that ever ran, which is exactly why this gap was invisible to CI.

**(session history)** `read-excel-file` was already the chosen library before the original Waltz-importer build session even started — it arrives pre-selected in the feature's plan doc, with no recorded comparison against alternatives (SheetJS, `exceljs`, `xlsx-populate`, etc.). The original build's own fixture generator (`scripts/fixtures/build-waltz-report-fixture.mjs`) built its "malformed" test fixture by truncating a valid `write-excel-file`-generated file's bytes — simulating corruption, not exercising any real-world streaming-writer output shape. Notably, that same build's `ce-doc-review` pass explicitly flagged (as an open limitation, not something fixed at the time) that the whole schema/fixture suite was validated against only one real Waltz export and could not catch drift from a different producer — the exact gap this bug fell through.

## Solution

Fixed in commit `720bf09` on branch `fix/waltz-oss-report-unzip-compat` (pushed to the `Github` remote; no PR opened, not yet merged as of this writing).

Swapped `parseWaltzReport()`'s sheet-reading layer from `read-excel-file` to `exceljs`. The unzip now happens once, up front, in a new `loadWaltzWorkbook()` (`src/utils/waltzReport.ts:205-218`):

```ts
async function loadWaltzWorkbook(buffer: Buffer): Promise<ExcelJS.Workbook> {
  const workbook = new ExcelJS.Workbook();
  try {
    // exceljs's index.d.ts globally re-declares `interface Buffer extends ArrayBuffer {}`, which
    // conflicts with @types/node's modern generic `Buffer<TArrayBuffer>` and makes every `Buffer`
    // reference in this file — including our own `buffer` parameter above — structurally mismatch
    // itself. A real Node Buffer either way; `any` here is routing around a broken vendored .d.ts,
    // not a runtime-unsafe cast.
    await workbook.xlsx.load(buffer as any);
  } catch (err) {
    throw new Error(`Could not read OSS report: ${err instanceof Error ? err.message : String(err)}`);
  }
  return workbook;
}
```

`parseWaltzReportInner` (`src/utils/waltzReport.ts:242-260`) now calls this once (line 247) and passes the resulting `ExcelJS.Workbook` down to `readNamedSheet`/`readOptionalNamedSheet` (lines 251, 259-260), instead of the old design where `read-excel-file`'s `readSheet(buffer, sheetName)` re-unzipped the whole archive on each of the three sheet reads.

Because `exceljs` hands back raw `ExcelJS.Cell` values rather than schema-validated rows, `read-excel-file`'s `Schema<T>` shape and `SheetNotFoundError` type were re-implemented locally and minimally (`src/utils/waltzReport.ts:59-92`):

```ts
type ColumnType = typeof String | typeof Number;
interface ColumnDef {
  column: string;
  type: ColumnType;
  required: boolean;
}
type Schema<T> = { [K in keyof T]: ColumnDef };
// ...
class SheetNotFoundError extends Error {
  constructor(sheetName: string, availableSheets: string[]) {
    super(`Sheet "${sheetName}" not found. Available sheets: ${availableSheets.join(', ') || '(none)'}`);
    this.name = 'SheetNotFoundError';
  }
}
```

`readNamedSheet` (`src/utils/waltzReport.ts:137-181`) walks the worksheet's header row via `headerIndex()` (`waltzReport.ts:125-132`) and its data rows via `worksheet.eachRow`, mapping cells to schema fields with `cellToString`/`cellToNumber` (`waltzReport.ts:97-122`, which resolve `exceljs`'s richer cell-value shapes — rich text runs, hyperlinks, formula results, dates — down to plain string/number), and preserves the exact pre-existing error strings:

```ts
if (errors.length > 0) {
  throw new Error(`OSS report sheet "${sheetName}" has invalid rows: ${errors.join('; ')}`);
}
```

and, at the call site in `parseWaltzReportInner` (`waltzReport.ts:250-257`):

```ts
try {
  remediations = readNamedSheet(workbook, REQUIRED_SHEET, componentRemediationsSchema);
} catch (err) {
  if (err instanceof SheetNotFoundError) {
    throw new Error(`OSS report is missing the required "${REQUIRED_SHEET}" sheet. (${err.message})`);
  }
  throw err;
}
```

`package.json` now depends on `"exceljs": "^4.4.0"`; `read-excel-file` has been removed from dependencies entirely (`write-excel-file`, the fixture generator, is unaffected — it's a writer with no unzip path).

## Why This Works

`read-excel-file`'s Node backend (`unzipper-esm`) is a **sequential/streaming ZIP reader**: it walks local file headers in file order and trusts each header's declared entry size to know where the next header starts. A legal ZIP variant — general-purpose flag bit 3, "deferred size to a trailing data descriptor" — is commonly produced by streaming XLSX writers (e.g. Java's Apache POI `SXSSFWorkbook`, a common producer of enterprise reporting exports) that don't know an entry's compressed size until they've finished writing it. A sequential reader that doesn't correctly special-case this loses sync partway through the archive and throws (`INVALID_SIGNATURE`/`FILE_ENDED`).

`exceljs`'s `workbook.xlsx.load(buffer)` reads the archive via the `jszip` package's `JSZip.loadAsync()`, which is **central-directory-first**: it locates every entry by reading the ZIP's End-Of-Central-Directory record at the end of the file, then jumps directly to each entry — the same strategy Excel's own OOXML reader uses. This has no dependency on local-header declared sizes at all, so deferred-size/data-descriptor entries simply don't matter to it. The fix isn't a different ZIP implementation with better error handling — it's a structurally different parsing strategy that sidesteps the exact assumption the old backend depended on.

## Prevention

- **The fixture-generation blind spot is structural and remains open.** Every `.xlsx` fixture in this repo (`scripts/fixtures/build-waltz-report-fixture.mjs`) is generated via `write-excel-file` — the same author's sibling package to the now-removed `read-excel-file`. A writer and reader from the same small ecosystem will always agree on ZIP layout by construction, so this class of "real producer writes something spec-legal but library-unfriendly" bug cannot be caught by this repo's own fixtures no matter which parsing library is used downstream. A future Waltz schema/format change, or any other real-world `.xlsx` producer, could reintroduce an equivalent "green in CI, broken for real users" gap. **(session history)** This exact limitation was already flagged as an open risk during the original Waltz-importer build's own doc-review pass — it went unaddressed at the time and is precisely the gap this bug fell through, which is worth remembering the next time a similar "validated against one real export" caveat shows up in a review.
- If it recurs: obtaining the actual failing file before reasoning from library internals is the fastest path. The diagnostic questions used here (does it open in Excel with no password prompt? plain local file or cloud-synced? has this worked before?) are a fast way to triage without the file in hand, but reproduction beats theory.
- **A synthetic fixture reproducing the exact byte-level defect (data-descriptor ZIP entries) was deliberately not created.** Hand-constructing one would encode an unconfirmed theory about the precise trigger as proven test coverage, which risks false confidence more than it adds real protection — the theory is well-evidenced (matches `unzipper-esm`'s own error taxonomy and a known class of streaming-writer output) but was never confirmed by reproduction against the actual failing file, since the user could not share it. Verify against the real file when possible; don't launder a plausible theory into test coverage that claims more certainty than exists.
- **Verification performed:** all 26 pre-existing `src/test/waltzReport.test.ts` tests — including the malformed-file (`toThrow(/could not read|invalid/i)`) and missing-required-sheet (`toThrow(/ComponentRemediations/)`) error-message assertions — passed unchanged with zero test modifications, confirming full behavioral parity for every previously-tested path. Full suite: 28 test files / 962 tests green; `npm run compile` clean; `npm run bundle` succeeds. **Not independently verified against the real-world failing file** — that remains open until the user can confirm against their actual report.
