# Onboarding

How a first-time user of Ticket Sidekick discovers what the extension can do
and gets to a working first ticket or PR review without reading the README
first.

> **Direction.** The Jira and Bitbucket tools, the `/ts-jira` and `/ts-bitbucket` skills and the boards are the product. The extension declares no chat participant: `@jira` was removed on 2026-11-16 and `@bitbucket` on 2026-11-23, with their slash commands, follow-up chips, disambiguation and greeting fallback. See [`docs/architecture/boards-and-sessions.md`](architecture/boards-and-sessions.md).

## Jira tools

Every Jira tool an agent calls is a VS Code language model tool (an "extension tool") registered by `src/tools/registerJiraTools.ts` from one catalog; each is declared once in `package.json`, generated by `scripts/sync-tools.mjs`. There is no MCP server.

- **The tools** read (`jira_check_connection`, `jira_view_ticket`, `jira_find_tickets`, `jira_list_my_filters`, `jira_workflow`, `jira_list_templates`, `jira_list_fields`, `jira_check_required_fields`, `jira_load_ticket`), open a board (`jira_open_board`) or change a ticket (`jira_move_ticket`, `jira_create_ticket`, `jira_add_comment`, `jira_update_field`, `jira_upload_attachment`). Their definitions live in [`src/tools/jiraTools/`](../src/tools/jiraTools/) (`catalog.ts` lists them; `toolNames.ts` holds the names any message text uses). See [`docs/architecture/boards-and-sessions.md`](architecture/boards-and-sessions.md) for the design and [`docs/manual/copilot-tools.md`](manual/copilot-tools.md) for the user-facing list; a new tool needs a row there (`src/test/userDocsSync.test.ts` checks the catalog against it).
- **Skills** (`contributes.chatSkills`, from `skills/<name>/SKILL.md`) build on the tools: `/ts-jira-brief` writes a developer brief of a ticket, `/ts-jira-create` creates one with the user, and `/ts-jira <command>` runs one tool the user names; `/ts-jira help brief` and `help create` print `help-brief.md` and `help-create.md` from its folder, so the other skills' names stay out of the router's own text. `/ts-jira-brief` and `/ts-jira` are explicit-only (`disable-model-invocation: true`), since a model without thinking ran a model-invocable brief skill in place of other requests; `/ts-jira-create` stays model-invocable on purpose, so a plain request for a new ticket goes through a template and a draft instead of a bare create. `src/test/skillsGuard.test.ts` keeps every contributed skill naming only catalog tools, with a frontmatter `name` equal to its folder, and model invocation off exactly for the `ts-` skills other than `ts-jira-create`.

Every tool is thin glue over `TicketService` (→ `IJiraClient` → `JiraApiClient`), `WorkflowService` and `TemplateService`, the same services the boards use. All of them run their Jira work through `runJiraTool` (`src/tools/jiraTools/runJiraTool.ts`): without a configured Jira they answer with `buildJiraNotConfiguredMessage(config)`; each Jira request has a time limit; a failure reaches the agent as the HTTP status and a short reason only, while the full error is logged under the `tools.jira` scope.

### Approvals

Tools that only read Jira carry `readOnlyHint` and run without asking. Every other tool (the five that change Jira carry `destructiveHint`; load ticket carries neither, since it writes only local files) returns a confirmation from `prepareInvocation`: the tool's title and every input value as plain text (`src/tools/jiraToolConfirmation.ts`), which VS Code shows unless the user turned on auto-approve. The write tools also report what they changed: move ticket names the status it came from and each transition, update field quotes the previous value, and create ticket lists the template fields it applied. A change to several tickets is never a tool call: the agent opens the ticket list board with the change proposed.

### Safeguards for agent-supplied input

- **Ticket keys** are checked with `isSafePathSegment()` ([`src/tools/pathSafety.ts`](../src/tools/pathSafety.ts)) before use, since they are put into request URLs and local paths.
- **Uploads** accept only a file that, with symlinks resolved, lies inside an open workspace folder, with no dotfile or dotfolder segment, up to 25 MB. An agent-supplied path is otherwise a way to send an arbitrary local file to Jira.
- **Duplicate writes** ([`src/tools/recentCallGuard.ts`](../src/tools/recentCallGuard.ts), through `writeGuard.ts`): create ticket, add comment and upload attachment create something new per call, so the same call repeated within a minute is skipped. The guard lives in the tools' long-lived dependencies, built once at activation. A call that wrote nothing releases its claim at once, so a real retry goes through; a write that timed out keeps it, since Jira may still have made the change, and its answer says so.
- **Never-guess issue type:** without an issue type or a template that sets one, create ticket lists the project's issue types (`TicketService.getIssueTypes`) and creates nothing. See [`docs/solutions/logic-errors/combined-create-list-silently-guesses-issue-type-and-drops-no-template-fallback.md`](solutions/logic-errors/combined-create-list-silently-guesses-issue-type-and-drops-no-template-fallback.md) for the failure mode this must not repeat.
- **Moves that stop partway:** each step of a move is a real Jira write, so a failed step leaves the ticket at an intermediate status. Move ticket reports where it landed and never retries. When no path is known, it discovers the workflow once (`discoverAndCacheWorkflow`) and tries again; the chat `transition` operation shares the same `resolveAndApplyTransition()` ([`src/services/WorkflowService.ts`](../src/services/WorkflowService.ts)).

### No session memory

Tools carry no session state between calls; work that needs state is a board's session. Write tools take a fully specified ticket or project key; only view ticket and load ticket fall back to the key in the current git branch.

## Bitbucket tools

The Bitbucket tools are VS Code language model tools from one vscode-free catalog, [`src/tools/bitbucketTools/`](../src/tools/bitbucketTools/) (`catalog.ts` lists them, `toolNames.ts` holds the names), registered by `src/tools/registerBitbucketTools.ts`. Their `package.json` entries are generated with the Jira tools' by `scripts/sync-tools.mjs`; `src/test/toolManifest.test.ts` fails when they differ.

- **Read:** `bitbucket_check_connection`, `bitbucket_getPullRequest`, `bitbucket_getPullRequestDiff`, `bitbucket_token_usage`, and `bitbucket_read_findings`, which reads a review stored by the review board (the summary, the findings list, or one finding with its code, explanation and draft).
- **Open a board:** `bitbucket_open_review` opens the review board of a pull request and answers as soon as it is open. The review runs on the board; the agent reads its result with `bitbucket_read_findings` afterwards, so a tool call never stays open for the minutes a review can take.
- **Write:** `bitbucket_postComment` posts a general comment after a confirmation that shows the whole comment.

The tools are always offered. Called before Bitbucket is set up, a tool answers with the missing setup step, never a raw `BitbucketApiError`. The user-facing list is [`docs/manual/agent-mode-tools.md`](manual/agent-mode-tools.md).

**`/ts-bitbucket`** (`skills/ts-bitbucket/SKILL.md`) is an explicit-only command router like `/ts-jira`: `review <url> [question]`, `check`, `usage` and `help`; `help review` prints `help-review.md` from its folder. `src/test/skillsGuard.test.ts` checks that each row names a tool that exists.

## Getting-Started walkthrough: Jira

`contributes.walkthroughs` in `package.json` declares a "Ticket Sidekick:
Jira" walkthrough (id `ticket-sidekick.jiraGettingStarted`) that takes a new
user from zero Jira config to a real first ticket. Every step completes on
real extension state via VS Code's native `completionEvents` — never a
static checklist a user has to tick off by hand (R12). Step markdown bodies
live in `walkthroughs/jira/*.md`; each links (or runs) the real
setting/command it describes.

| # | Step id | What it asks for | Completion signal |
| --- | --- | --- | --- |
| 1 | `jiraBaseUrl` | `ticketSidekick.jira.baseUrl` setting | `onSettingChanged:ticketSidekick.jira.baseUrl` |
| 2 | `jiraCredentials` | A Data Center PAT or Cloud email+API token, via `ticket-sidekick.setDataCenterToken` / `ticket-sidekick.configureCloud` | `onContext:ticketSidekick.jiraCredentialsSet` (U1's context key, kept in sync in `extension.ts`) |
| 3 | `jiraDefaultProject` | `ticketSidekick.jira.defaultProject` setting | `onSettingChanged:ticketSidekick.jira.defaultProject` |
| 4 | `jiraWorkflow` | `/ts-jira workflow <KEY>`, which shows a ticket's reachable statuses and discovers the workflow the first time | `onContext:ticketSidekick.workflowViewed` — set by `src/tools/registerJiraTools.ts` after a successful `jira_workflow` call (`src/tools/walkthroughProgress.ts`) |
| 5 | `jiraFirstTicket` | Creating a template from a ticket (`/ts-jira-template`) and a ticket from it, or `/ts-jira-create` directly | `onContext:ticketSidekick.firstTicketCreated` — set after a successful `jira_create_ticket` call, the same way |
| 6 | `jiraCopilotTools` | The Jira tools, `/ts-jira help` and the boards | `onCommand:ticket-sidekick.boards.sessions` |

**First-touch auto-open (KTD11).** `extension.ts`'s `activate()` opens this
walkthrough automatically once, guarded by the `globalState` flag
`ticketSidekick.jiraWalkthroughSeen` — set the first time `activate()` runs
and never re-checked false afterward, so the walkthrough never reopens on
a later VS Code start. The Bitbucket walkthrough (a separate contribution,
added in a later unit) does not auto-open.

Each step's button opens Copilot Chat pre-filled with the relevant `/ts-jira`
command via `workbench.action.chat.open` (the same command
`extension.ts`'s `.eml` import command uses to open
chat with a fixed query), or runs the credential-setup command directly.

## Getting-Started walkthrough: Bitbucket

`contributes.walkthroughs` in `package.json` also declares a second, separate
"Ticket Sidekick: Bitbucket" walkthrough (id
`ticket-sidekick.bitbucketGettingStarted`) — a sibling entry to the Jira one
above, not merged into it (KTD10). It takes a new user from zero Bitbucket
config to a real first PR review, with the same rule as Jira's: every step
completes on real extension state via VS Code's native `completionEvents`,
never a static checklist (R12). Step markdown bodies live in
`walkthroughs/bitbucket/*.md`; each links (or runs) the real setting/command
it describes.

| # | Step id | What it asks for | Completion signal |
| --- | --- | --- | --- |
| 1 | `bitbucketBaseUrl` | `ticketSidekick.bitbucket.baseUrl` setting (Data Center only) | `onContext:ticketSidekick.bitbucketCredentialsSet` |
| 2 | `bitbucketCredentials` | A Data Center PAT or Cloud username+App Password, via `ticket-sidekick.setBitbucketDataCenterToken` / `ticket-sidekick.configureBitbucketCloud` | `onContext:ticketSidekick.bitbucketCredentialsSet` (U1's context key, kept in sync in `extension.ts`) |
| 3 | `bitbucketFirstReview` | Reviewing a real PR on the review board (`Ticket Sidekick: Review a pull request`) | `onContext:ticketSidekick.firstReviewCompleted` — set by the review board's `onReviewCompleted` hook (`src/boards/registerBoards.ts`) when a review finishes, never on a stopped or failed run |

**Base URL step's completion signal (KTD9).** Data Center needs
`ticketSidekick.bitbucket.baseUrl` set; Cloud needs no base URL at all — it
always talks to the fixed `api.bitbucket.org` host. Rather than add a new
context-key listener to distinguish the two, this step reuses the existing
`ticketSidekick.bitbucketCredentialsSet` signal: `ConfigService.isBitbucketConfigured()`
(U1's gate, already backing that key) already requires `baseUrl` **and**
`token` for Data Center but only `token` for Cloud, so the moment that key
goes true, a Data Center user's base URL is genuinely set and a Cloud user's
(inapplicable) base-URL step correctly completes alongside credentials —
with no separate signal to invent or keep in sync.

**Never auto-opened (KTD11).** Unlike the Jira walkthrough, this one has no
`globalState`-guarded auto-open block in `extension.ts` — it's reachable only
from VS Code's Get Started page, by design.

Each step's button opens Copilot Chat pre-filled with `/ts-bitbucket check`
via `workbench.action.chat.open`, runs the credential-setup command, or opens
the review board's start screen (`ticket-sidekick.boards.openReview`).
