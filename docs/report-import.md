# Report Import (EML, Veracode, Waltz)

How `@jira` turns an `.eml` email, a Veracode Detailed Report, or a Waltz OSS
Report into Jira tickets.

The code lives in:

- [`src/utils/emlParser.ts`](../src/utils/emlParser.ts) — `.eml` parsing (`postal-mime`), plus `parseEmlFile()` (one file → one batch item) and the `EmailImportItem`/`EmailReviewRow` types.
- [`src/participant/jira/emailHandler.ts`](../src/participant/jira/emailHandler.ts) — batch email-to-ticket chat flow (the `email` `ReportImportDescriptor`) and the untouched single-file comment-attach flow.
- [`src/utils/reportImport.ts`](../src/utils/reportImport.ts) — shared, `vscode`-free primitives used by all three importers, including `BATCH_LIMIT` and `resolveMaxReportBytes()` (turns a configured `maxReportSizeMB`/`maxBatchSizeMB` setting into a validated byte limit, falling back to a default when the value is missing or out of range).
- [`src/participant/jira/reportImportHandler.ts`](../src/participant/jira/reportImportHandler.ts) — shared session-flow orchestration for all three report importers; dedup fields on `ReportImportDescriptor` are optional, and `buildTicketFields`/`afterCreate` let an importer with no `labels`/`descriptionWiki` concept (email) still drive the same per-group creation step (`createNewRows`).
- [`src/utils/veracodeReport.ts`](../src/utils/veracodeReport.ts) / [`src/participant/jira/veracodeHandler.ts`](../src/participant/jira/veracodeHandler.ts) — Veracode-specific parsing and thin wrapper.
- [`src/utils/waltzReport.ts`](../src/utils/waltzReport.ts) / [`src/participant/jira/waltzHandler.ts`](../src/participant/jira/waltzHandler.ts) — Waltz-specific parsing and thin wrapper.
- [`src/services/TicketService.ts`](../src/services/TicketService.ts) — `searchTicketsRaw` (dedup search), `createTicket` (batch creation), and `updateLabels()`/`addComment()`/`linkIssues()` (the Already-ticketed `update` and `follow-up` actions) backing all three importers.
- [`src/participant/sessionState.ts`](../src/participant/sessionState.ts) — `pickEmailOption()`, reused by all three importers for template/issue-type selection; `buildReviewPage()`/`parseReviewPageNav()`/`applyReviewSessionToggle()` (paging), the stale-ticket-key toggle helpers, the stale close's target-pick helpers (`buildStaleTargetOptions()`, `planStaleTransitions()`, `StaleCloseSession`), and the overview-hub screens and per-screen reply parsers (`buildImportScreen()`, `parseImportReviewReply()` — see "Overview and group screens" below).
- [`src/participant/jira/cleanupHandler.ts`](../src/participant/jira/cleanupHandler.ts) — `transitionTickets()` (extracted, reused by the stale-ticket close step) and `buildStaleTicketGroups()` (groups stale tickets by issue type with their matching cleanup rules and a workflow-graph snapshot for the close-time target pick).
- [`src/participant/jira/ticketContext.ts`](../src/participant/jira/ticketContext.ts) — `resolveIssueTypeOrPrompt()`/`AwaitIssueTypeResume`, the park-ask-resume pattern the stepped stale-ticket close is modeled on.

## EML email import (batch)

Users download `.eml` files from OWA via **More actions → Download message** and import one or more of them in a single run — every selected file becomes a candidate ticket, reviewed together and created as a batch. See `docs/plans/2026-09-03-2108-feat-batch-email-import-plan.md` for the batching decisions and rationale.

Email import is the third `ReportImportDescriptor` kind (`descriptorKind: 'email'`), reusing the same shared session flow, review screen, and batch-creation machinery the OSS/vulnerability importers below already share — see that section for the mechanics common to all three. Email supplies no dedup fields (there is no per-email dedup key, so the "already ticketed" search step is skipped entirely) and its own `buildTicketFields` (subject → summary, `buildEmailJiraWiki(markdownBody)` → description) and `afterCreate` hook (per-ticket attachment upload, then the `ticketSidekick.email.deleteEmlAfterImport` cleanup step).

### Import flow

1. Any of three entry points: Command Palette → **Ticket Sidekick: Create Jira ticket from email (.eml)** (multi-select file picker), `@jira create from email` / `@jira import email` in chat (multi-select), or `@jira add email` with no ticket key in the prompt (also routes into batch creation — only a prompt naming a ticket key stays single-file, adding the email as a comment instead)
2. Before any file is read: the selected-file count is checked against `BATCH_LIMIT` (50), and the selected files' total size against `ticketSidekick.email.maxBatchSizeMB` (default 150 MB, configurable 1–500 MB). Either cap being exceeded rejects the whole selection with a message naming the cap actually in effect
3. `parseEmlFile(filePath)` (`src/utils/emlParser.ts`) reads and parses each selected file (via `parseEml`/postal-mime), converting the HTML body to Markdown (`htmlToMarkdown`) with `[📎 name]` placeholders for inline images. A file that fails to parse is reported immediately and excluded — the rest of the batch still proceeds
4. `EmailTemplateSelectionSession` stored in `workspaceState('jira.session.emailTemplateSelection')`; chat opened (or continued) with the template/issue-type picker — **one shared template/issue type for the whole batch**, not a per-email choice
5. `EmailReviewSession` stored in `workspaceState('jira.session.emailReview')` — the review table lists every email's subject and non-inline attachment names; an email batch only ever has a New group, so it opens straight on the New screen (no overview, see "Overview and group screens"); user replies **ok** / `create tickets` / a list of row ids to toggle inclusion / `include all` or `exclude all` (see "Bulk include/exclude") / `done`
6. On **ok** / `create tickets`, one ticket is created per included email (skip-and-continue: a single email's creation failure is reported and does not stop the rest), each with `buildEmailJiraWiki(markdownBody)` as the description and its own attachments uploaded afterward; if `ticketSidekick.email.deleteEmlAfterImport: true`, the source `.eml` is deleted after each successful creation (non-fatal)

The "add email as a comment to an existing ticket" flow (a ticket key present in the `@jira add email ...` prompt) is unaffected by any of the above — it stays single-file, using `EmailContentSession`/`workspaceState('jira.session.emailContent')` and `handleEmailContentSession`.

### `pickEmailOption` helper

`pickEmailOption(n, templates, issueTypes)` in `sessionState.ts` maps a 1-based user reply index to a template or issue type pick. Templates occupy indices 1..N, issue types N+1..N+M. Returns `{ kind: 'template', name, issueType }` or `{ kind: 'type', issueType }` or `null` if out of range.

## OSS/vulnerability report import (Veracode + Waltz) and email

Veracode, Waltz, and email import share one implementation — `src/participant/jira/reportImportHandler.ts` + `src/utils/reportImport.ts` — for session flow, dedup search, the review-table/toggle-reply UX, and batch ticket creation. Each importer supplies only its own parser, config, and ticket-field-building specifics via a `ReportImportDescriptor` passed from its thin wrapper (`veracodeHandler.ts`/`waltzHandler.ts`/`emailHandler.ts`). This means: dedup search is fault-tolerant per chunk and JQL-quoted where an importer has a dedup key (Veracode/Waltz), or skipped entirely where it doesn't (email); a picked template that vanishes before the user replies produces the same warning for all three; all three link to each newly created ticket in the per-item progress output, and any importer may supply an `afterCreate` hook for per-row work after ticket creation (email uses this for attachment upload). A behavior difference between importers on shared ground is a bug, not a feature — see `docs/plans/2026-08-13-001-refactor-consolidate-report-importers-plan.md` for the original Veracode/Waltz consolidation rationale, `docs/plans/2026-09-03-2108-feat-batch-email-import-plan.md` for email's extension of the same pattern, `docs/plans/2026-09-14-1726-feat-veracode-fold-page-stale-plan.md` for same-line folding, paging, and the stale-ticket check, `docs/plans/2026-09-30-0902-feat-import-ticket-updates-parity-plan.md` for the per-row Already-ticketed actions, and `docs/plans/2026-09-23-1400-feat-report-import-overview-hub-plan.md` for the overview and per-group screens, and `docs/plans/2026-09-27-1949-feat-stale-ticket-target-pick-plan.md` for the close-time target pick on the Stale screen.

The "New — will create" section no longer pre-caps at `BATCH_LIMIT` before the session is built (Veracode and Waltz alike) — it holds every matched "new" candidate and is **pageable** (see "Paging the New section" below); the "Already ticketed" section is unaffected, shown in full as before. Both importers also run a **reverse stale-ticket check** on every import (see "Stale-ticket detection and inline close" below).

### Veracode report import

Users export a Detailed Report XML from Veracode and import it via the VS Code command or directly from chat (`@jira import veracode report`).

1. Command Palette → **Ticket Sidekick: Create Jira tickets from Veracode report (.xml)** (or trigger from chat, which opens its own file picker)
2. `parseVeracodeReport(xml)` (own parser, `fast-xml-parser`-based) extracts all `<staticflaws>` entries; rejected up front if the file exceeds `ticketSidekick.veracode.maxReportSizeMB` (default 50 MB, configurable 1–200 MB) or contains a `<!DOCTYPE`/`<!ENTITY` declaration. `issueId` and `cweId` are each validated numeric (`ISSUE_ID_PATTERN`/`CWE_ID_PATTERN`) at parse time — a malformed `cweId` becomes `null` rather than surviving into a generated CWE-database URL
3. `filterFlaws()` applies `ticketSidekick.veracode.minSeverity` and `ticketSidekick.veracode.includeRemediationStatuses`
4. `VeracodeTemplateSelectionSession` stored in `workspaceState('jira.session.veracodeTemplateSelection')`; chat opened with `@jira import veracode report`
5. User picks a template or issue type (`pickEmailOption()`, reused from the email flow) → `FieldResolver.resolve()` resolves the template's fields
6. Flaws sharing the same source file + line number **fold** into one review row (see "Same-line finding folding" below) before dedup ever runs.
7. De-dup search (via the shared `reportImport.ts` primitives): `TicketService.searchTicketsRaw` is called in chunks of 40 issue ids with a quoted `labels in ("veracode-issue-<id>", ...)` JQL clause — a folded group searches for *every* member flaw's label, and a match on any one of them counts the whole group as already-ticketed; a failed chunk is logged and skipped without discarding matches already found by other chunks; matches become the "Already ticketed" group, whose rows each get a proposed action (see "Already-ticketed rows: per-row actions" below)
8. A **reverse stale-ticket search** (see "Stale-ticket detection and inline close" below) runs against the project's other open `veracode`-labeled tickets.
9. `VeracodeReviewSession` stored in `workspaceState('jira.session.veracodeReview')`; the review opens on the overview (or directly on the only group that has rows) — see "Overview and group screens" below. The New group holds every matched candidate and is **pageable** (see "Paging the New section" below) rather than pre-capped
10. On `create tickets` (or **ok**) on the New screen, up to `BATCH_LIMIT` tickets are created via the existing `TicketService.createTicket` — one per included row (one row per folded group, not per flaw), each labeled `veracode`, one `veracode-issue-<id>` per folded flaw, one `cwe-<id>` per distinct CWE among them (merged with any template labels), with a Markdown-authored description (converted to Jira wiki via `markdownToJiraWiki()`, every untrusted field sanitized) covering every folded flaw's own Severity, CWE + link, Description, and Recommendation under its own heading, plus a shared Location and Veracode Issue ID list; each per-ticket progress line links to the created ticket when a Jira base URL is configured. Nothing in the other groups is touched.

#### Same-line finding folding

Veracode flaws sharing the same source file and line number fold into a single review row and, on creation, a single ticket — regardless of CWE or category — instead of one row/ticket per flaw (`groupFlawsByLocation()` in `veracodeReport.ts`). A flaw missing a source file or line number is never folded with another flaw, including another flaw that also lacks a location. The full ticket description for a folded group is built lazily, only when a row is actually confirmed into creation, rather than for every candidate the report matches. Folding is Veracode-only — a Waltz ticket already covers a whole component, so there's no same-line case to fold.

#### Bulk include/exclude (all three importers)

The New screen offers two bulk controls — **`include all`** and **`exclude all`** (links rendered under the New table, shown only when at least one New row exists) — that set every New row on the currently visible page to included or excluded in one action, instead of toggling rows one at a time. They live in the shared screen renderer (`buildNewGroupScreen()`), so all three importers get them with no per-importer gating. The reply tokens are exact-match only (`parseBulkNewRowReply()`, checked by `parseNewGroupReply()` after the create/exit words and page-nav, before row-id parsing) and verified disjoint from every other reply vocabulary. Like a per-row New toggle, a bulk set is **page-local**: it touches `session.rows` only, never `allRows`, so navigating away from a page and back resets that page's New rows to default-included; other groups and pages are untouched. The one exception: when `create tickets` runs, the visible page's exclusions are written into `allRows` first, so an excluded row stays excluded afterwards.

#### Already-ticketed rows: per-row actions (Veracode + Waltz)

The dedup search reads every result page of each label chunk (`fetchAllPages()`, capped at 1000 tickets per chunk) and keeps every ticket per dedup key (`findAlreadyTicketed()` returns a `DedupMap` of `DedupTicket` lists with labels, resolution, creation date and status). For an already-ticketed item, `buildReviewRows()` unions the labels of all its tickets, asks the importer's `changeTracking.describe()` what changed, and picks the row's **target**: the newest unresolved ticket (latest `created`, ties to the highest key number), or the newest ticket when all are resolved (`pickTargetTicket()`).

A change is a finding id none of the item's tickets record — a Veracode flaw's `veracode-issue-<id>` label, or a Waltz CVE's `oss-cve-<id>` label — or, for Waltz, a worst rating higher than the recorded `oss-rating-<rating>` label. A Waltz ticket with neither kind of record label (created before this feature) is a **baseline**. New Waltz tickets get these record labels at creation.

`deriveTicketedActions()` sets each row's allowed actions and default:

- no change → `leave` (offers `re-create`, `leave`)
- change, some ticket open → `update`
- change, every ticket resolved → `follow-up`, or `update` when the only change is a rating rise
- baseline → `update`, which records the current labels only — no comment, no summary change

`follow-up` is offered only with new findings. The Action cell shows every allowed action as its own link with the current one in bold. The user changes a row with `<row id> <action>` or `all <action>` and replies `apply` (or `ok`); `update tickets` / `re-create tickets` (and the legacy `update existing tickets`) run only the rows set to that action. At most `BATCH_LIMIT` rows run per reply.

- **update** (`TicketService.updateLabels()`, one read-merge-write): adds the missing record labels, replaces any old `oss-rating-*` label when it adds a new one, rewrites a Waltz summary ending in ` — <old rating>` (optionally followed by ` (follow-up to <KEY>)`), then posts one comment listing the new findings and any rating rise. A summary the user renamed is left alone and the comment says so. A comment that fails after the labels were written is reported as "labels updated, comment failed".
- **follow-up**: creates a ticket with only the new findings (summary suffix ` (follow-up to <KEY>)`) and links it "Relates" to the target (`TicketService.linkIssues()`). A failed link keeps the ticket and shows a warning.
- **re-create**: creates a full ticket as for a New row.

A finished row shows its result in place of links and is skipped by later runs; a failed row keeps its links for a retry. Email has no change tracking and keeps its screen unchanged. See `docs/plans/2026-09-30-0902-feat-import-ticket-updates-parity-plan.md`.

#### Known limitation

The multi-step vulnerability data-path trace shown in Veracode's web UI ("Injection Point → ... → Flaw") is **not present** in the Detailed Report XML format — confirmed by full XSD schema review and empirical inspection of a real report. Only the flaw's own `description` attribute (which sometimes names generic tainted-source APIs, but not the actual call chain) is available and is included (sanitized) in the ticket. Full data-path support would require a different Veracode API/export (e.g. the Findings REST API) and is out of scope for this feature.

### Waltz OSS report import

Users export an "OSS Report" `.xlsx` from Waltz (or a compatible SCA tool) and import it via the VS Code command or directly from chat (`@jira import oss report`).

1. Command Palette → **Ticket Sidekick: Create Jira tickets from OSS report (.xlsx)** (or trigger from chat, which opens its own file picker)
2. `parseWaltzReport(buffer)` (`exceljs`-based — `workbook.xlsx.load()`, which reads the ZIP via `jszip`'s central-directory-first parsing rather than a sequential/streaming reader, so it doesn't choke on real-world exports written by streaming XLSX writers; a prior `read-excel-file`/`unzipper-esm` build threw `Couldn't unzip \`.xlsx\` file contents` on exactly this class of file even though Excel opened it fine — see `docs/solutions/` for the write-up) joins the required `ComponentRemediations` sheet with the optional `VersionInstances`/`Vulnerabilities` sheets on `Component name and version`; guarded by `ticketSidekick.waltz.maxReportSizeMB` (default 50 MB, configurable 1–200 MB) and a `PARSE_TIMEOUT_MS` (15s) hard ceiling. The timeout is a `Promise.race`, not a true cancellation — it bounds how long the user waits before seeing an error on a pathological (e.g. decompression-bomb-style single-entry) `.xlsx`, but the underlying parse keeps consuming CPU/memory in the background after it fires; it does not itself prevent resource exhaustion
3. `filterComponents()` applies `ticketSidekick.waltz.minVulnRating` and `ticketSidekick.waltz.includeRemediationActions`
4. `WaltzTemplateSelectionSession` stored in `workspaceState('jira.session.waltzTemplateSelection')`; chat opened with `@jira import oss report`
5. User picks a template or issue type (`pickEmailOption()`, reused from the email flow) → `FieldResolver.resolve()` resolves the template's fields
6. De-dup search (via the shared `reportImport.ts` primitives): `TicketService.searchTicketsRaw` is called in chunks of 40 sanitized component labels with a `labels in ("oss-dep-...", ...)` JQL clause; matches become the "Already ticketed" group with per-row actions (see "Already-ticketed rows: per-row actions" above). A dedup-search failure degrades gracefully (empty dedup map + warning) rather than aborting the import
7. A **reverse stale-ticket search** (see "Stale-ticket detection and inline close" below) runs against the project's other open `oss-dependency`-labeled tickets.
8. `WaltzReviewSession` stored in `workspaceState('jira.session.waltzReview')`; the review opens on the overview (or directly on the only group with rows) exactly like Veracode's — see "Overview and group screens" below. The New group holds every matched (not-yet-ticketed) component and is **pageable** (see "Paging the New section" below) rather than pre-capped
9. On `create tickets` (or **ok**) on the New screen, up to `BATCH_LIMIT` tickets are created via the existing `TicketService.createTicket` — one per included component, labeled `oss-dependency` + a sanitized, hash-suffixed component label + one `oss-cve-<id>` label per CVE + one `oss-rating-<rating>` label (merged with any template labels), with a Markdown-authored description (converted to Jira wiki via `markdownToJiraWiki()`) covering max vuln rating, the single most critical CVE, affected artifacts (capped at 25, "+N more"), and a "Known vulnerabilities" table (capped at 10, "+N more"). Nothing in the other groups is touched.

#### Component labels

`sanitizeComponentLabel()` lowercases and hyphenates disallowed separators (dots pass through unchanged, so version numbers like `1.2.3` stay readable), then appends a 6-hex-char SHA-256-derived hash of the *raw* `nameVersion` — this keeps the label human-readable while making it collision-safe as the sole dedup key, since two distinct components (e.g. differing only in a separator character) can otherwise sanitize to the identical readable text.

#### Known limitation

The report's real-world schema (sheet names, column headers) was validated against a single inspected `.xlsx` export; a schema drift in a different Waltz version, report template, or locale would break parsing for some users with no test coverage to catch it in advance — tracked as an open question in the plan doc, not yet validated against a second real export.

### Overview and group screens (all three importers)

The review is split into up to three result groups — **New**, **Already ticketed**, **Stale** — so each kind of result has its own screen, reply vocabulary and action (`docs/plans/2026-09-23-1400-feat-report-import-overview-hub-plan.md`). The `ReviewSession` records which screen is showing (`view`), the groups that had rows when it was built (`groups`, fixed for the session), whether exactly one did (`singleGroup`), and the accumulated action outcomes (`outcomes`); `initImportViewState()` sets them once when the session is built.

- **Overview** (`buildImportOverview()`): one line per group with its count, what already happened to it (e.g. "50 created · 12 left", "1 closed") and an `open new` / `open already ticketed` / `open stale` link while it still has something to act on. A fully handled group stays listed with its outcome and no link. `done` (or a cancellation word) ends the import with a one-line summary of the outcomes.
- **Group screens** (`buildNewGroupScreen()`, `buildTicketedGroupScreen()`, `buildStaleGroupScreen()`): only that group's table and actions — `create tickets` (New), per-row actions plus `apply` (Already ticketed), `close tickets` (Stale) — plus `back` to the overview. After an action the per-item results stream and the overview returns.
- **Single group:** when exactly one group has rows (always the case for email), that screen opens directly, offers `done` instead of `back`, and re-shows itself after an action.
- **Reply parsing:** `parseImportReviewReply()` reads a reply only against the current screen's vocabulary — a row id on the Stale screen or a ticket key on the New screen is "didn't understand", never acted on, and a reply mixing vocabularies is rejected whole. Confirmation words (`ok`, `post it`, …) run the screen's single action: `create tickets` on New, `apply` on Already ticketed, `close tickets` on Stale; on the overview they are not accepted. Cancellation words go back to the overview (or end a single-group import). The command words are pinned disjoint from confirmation/cancellation words, row ids, ticket keys and page/bulk tokens by a unit test.
- **Superseded import:** a reply arriving after a newer import claimed the template-selection key closes the old review without acting (`sessionWasSuperseded()`).

### Paging the New section (Veracode + Waltz)

The "New — will create" review section holds every matched candidate up front (`ReviewSession.allRows` in `sessionState.ts`) rather than pre-capping before the session is built. `buildReviewPage(allRows, page)` slices out one page (`BATCH_LIMIT`, 50 rows) of "new" candidates plus every "already ticketed" row (that section is always shown in full, unpaged). Replying `next` / `prev` / `page <n>` (case-insensitive; `next page`/`previous page` also work) navigates — recognized ahead of the row-id toggle parser, so it never collides with a numeric reply. Each page defaults every one of its rows to included; navigating away discards any toggles made on a page the user has left, and `create tickets` (or **ok**) creates only the currently visible page's included rows — pick which page to create from by paging there first. Created rows then leave the New group, so the next page moves up and a repeated `create tickets` never creates a row twice. A bare numeric toggle only affects a row on the currently visible page; a number matching a row on a different page is unrecognized input, not a silent toggle or page jump. The bulk `include all` / `exclude all` controls (see "Bulk include/exclude") are page-local in the same way. The old "N more matched, re-run the import" message is replaced by "Page X of Y" wording; the per-confirm `BATCH_LIMIT`-tickets cap and its own message are unchanged.

For Veracode, a folded group's full ticket description is built lazily — only for a row the user actually confirms into creation — rather than for every candidate up front, since most of a large report's candidates are never paged to.

### Stale-ticket detection and inline close (Veracode + Waltz)

Every import run also searches the target project for open (`resolution is EMPTY`) tickets carrying the importer's marker label (`veracode` / `oss-dependency`) and flags one stale when every finding it covers is either absent from the current report or present but no longer matching the importer's own remediation filter (`includeRemediationStatuses` / `includeRemediationActions`). A folded, multi-finding ticket is flagged only once *all* of its findings are gone — one still-active finding keeps it off the stale list. `findStaleTickets()` in `reportImport.ts` runs one search per import, capped at `BATCH_LIMIT` (50) with the same "found N — showing first 50" truncation warning `@jira cleanup`'s analogous query gives when a project has more matches than that.

Stale tickets render on their own Stale screen, one per row with its issue type, toggled by full ticket key (e.g. `PROJ-123`) and defaulting to **unselected** — nothing transitions without an explicit toggle. On `close tickets` (or **ok**) on that screen, the user picks where the selected tickets go (`docs/plans/2026-09-27-1949-feat-stale-ticket-target-pick-plan.md`), through a stepped `StaleCloseSession` stored under `jira.session.staleResolution`:

1. **Issue type** — each run closes one issue type. When the selection spans several, the user first picks which one; the other types' tickets stay selected for a later close.
2. **Target** — every `.jira-templates.json` `cleanupRules` entry matching the project + issue type (listed first, as "rule name → target"), then every status the selected tickets can reach in the discovered workflow, alphabetically. A rule applies its own target and resolution; a plain status (including a non-final one like "Verification") applies only the status. When no rule matches and no selected ticket can reach any status, the close explains why and suggests `@jira discover workflow` instead of asking.
3. **Resolution** — asked once, only when the target is a closing status (`CLOSED_LIKE_STATES`: Done, Resolved, Closed, Won't Fix) and nothing else supplies one. `none` or `skip` sets no resolution.

Replying `back` (or a cancellation word; at the resolution step `skip` means "no resolution" instead) returns to the Stale screen with nothing transitioned. Transition paths are computed only after the pick, from the workflow-graph snapshot stored with the stale section, and run through the same `transitionTickets()` `@jira cleanup` uses (extracted from `cleanupHandler.ts`'s `executeCleanupBatch()` for reuse). A selected ticket already in the target, or with no path to it, is skipped with a note and deselected; a transitioned ticket is marked so a repeated close never transitions it twice. While tickets of another issue type are still selected, the Stale screen stays open after a run. A stale ticket is selectable when its project + issue type has a discovered workflow — no cleanup rule is needed. One with an unknown issue type or no discovered workflow still renders, with a note, but isn't offered as a toggle. The resolution names are fetched once when the stale section is built, so the close makes no Jira call before the transitions. Tickets moved to a non-final status stay open, so later imports list them again as ordinary stale rows.
