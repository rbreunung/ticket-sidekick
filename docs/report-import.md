# Report Import (EML, Veracode, Waltz)

How `@jira` turns an `.eml` email, a Veracode Detailed Report, or a Waltz OSS
Report into Jira tickets.

The code lives in:

- [`src/utils/emlParser.ts`](../src/utils/emlParser.ts) — `.eml` parsing (`postal-mime`), plus `parseEmlFile()` (one file → one batch item) and the `EmailImportItem`/`EmailReviewRow` types.
- [`src/participant/jira/emailHandler.ts`](../src/participant/jira/emailHandler.ts) — batch email-to-ticket chat flow (the `email` `ReportImportDescriptor`) and the untouched single-file comment-attach flow.
- [`src/utils/reportImport.ts`](../src/utils/reportImport.ts) — shared, `vscode`-free primitives used by all three importers, including `BATCH_LIMIT` and `resolveMaxReportBytes()` (turns a configured `maxReportSizeMB`/`maxBatchSizeMB` setting into a validated byte limit, falling back to a default when the value is missing or out of range).
- [`src/participant/jira/reportImportHandler.ts`](../src/participant/jira/reportImportHandler.ts) — shared session-flow orchestration for all three report importers; dedup fields on `ReportImportDescriptor` are optional, and `buildTicketFields`/`afterCreate` let an importer with no `labels`/`descriptionWiki` concept (email) still drive the same per-group creation step (`createNewRows`).
- The group actions sit beside it, each in its own module over the shared `importReviewScreen.ts` (screen streaming, `IMPORT_SESSION_KINDS`) and the descriptor types in `reportImportTypes.ts`: `importCreate.ts` (`createOne`, `createNewRows`), `importAddToTicket.ts` (`add … to <KEY>` and the rewrite plan the Already-ticketed `rewrite` shares), `importAccept.ts` (`accept`/`accepted`/`unaccept`), `importStaleClose.ts` (the Stale screen's close and its stepped ask) and `importTicketedActions.ts` (the Already-ticketed per-row actions). `reportImportHandler.ts` keeps the session build and the reply dispatch and re-exports the public entry points, so importers and tests import from it as before. The module graph is acyclic: types, then the leaf modules, then the stale and ticketed actions, then the handler.
- [`src/utils/veracodeReport.ts`](../src/utils/veracodeReport.ts) / [`src/participant/jira/veracodeHandler.ts`](../src/participant/jira/veracodeHandler.ts) — Veracode-specific parsing and thin wrapper.
- [`src/utils/waltzReport.ts`](../src/utils/waltzReport.ts) / [`src/participant/jira/waltzHandler.ts`](../src/participant/jira/waltzHandler.ts) — Waltz-specific parsing and thin wrapper.
- [`src/services/TicketService.ts`](../src/services/TicketService.ts) — `searchTicketsRaw` (dedup search), `createTicket` (batch creation), and `updateLabels()`/`addComment()`/`linkIssues()` (the Already-ticketed `update` and `follow-up` actions) backing all three importers.
- [`src/participant/sessionState.ts`](../src/participant/sessionState.ts) — `pickEmailOption()`, reused by all three importers for template/issue-type selection; `buildReviewPage()`/`parseReviewPageNav()`/`applyReviewSessionToggle()` (paging), the stale-ticket-key toggle helpers, the stale close's target-pick helpers (`buildStaleTargetOptions()`, `planStaleTransitions()`, `StaleCloseSession`), and the overview-hub screens and per-screen reply parsers (`buildImportScreen()`, `parseImportReviewReply()` — see "Overview and group screens" below).
- [`src/participant/jira/cleanupHandler.ts`](../src/participant/jira/cleanupHandler.ts) — `transitionTickets()` (extracted, reused by the stale-ticket close step) and `buildStaleTicketGroups()` (groups stale tickets by issue type with their matching cleanup rules and a workflow-graph snapshot for the close-time target pick).
- [`src/participant/jira/ticketContext.ts`](../src/participant/jira/ticketContext.ts) — `resolveIssueTypeOrPrompt()`/`AwaitIssueTypeResume`, the park-ask-resume pattern the stepped stale-ticket close is modeled on.

## EML email import (batch)

Users download `.eml` files from OWA via **More actions → Download message** and import one or more of them in a single run — every selected file becomes a candidate ticket, reviewed together and created as a batch. See `docs/plans/2026-09-03-2108-feat-batch-email-import-plan.md` for the batching decisions and rationale.

Email import is the third `ReportImportDescriptor` kind (`descriptorKind: 'email'`), reusing the same shared session flow, review screen, and batch-creation machinery the OSS/vulnerability importers below already share — see that section for the mechanics common to all three. Email supplies no dedup fields (there is no per-email dedup key, so the "already ticketed" search step is skipped entirely) and its own `buildTicketFields` (subject → summary, `buildEmailJiraWiki(markdownBody)` → description) and `afterCreate` hook (per-ticket attachment upload, then the `ticketSidekick.email.deleteEmlAfterImport` cleanup step).

### Import flow

1. Any of three entry points: Command Palette → **Ticket Sidekick: Create Jira ticket from email (.eml)** (multi-select file picker), `@jira create from email` / `@jira import email` in chat (multi-select), or `@jira add email` with no ticket key in the prompt (also routes into batch creation — only a prompt naming a ticket key stays single-file, adding the email as a comment instead)
2. Before any file is read: the selected-file count is checked against `BATCH_LIMIT` (50), and the selected files' total size against `ticketSidekick.email.maxBatchSizeMB` (default 150 MB, configurable 1–500 MB). Either cap being exceeded rejects the whole selection with a message naming the cap actually in effect
3. `parseEmlFile(filePath)` (`src/utils/emlParser.ts`) reads and parses each selected file (via `parseEml`/postal-mime), converting the HTML body to Markdown (`htmlToMarkdown`) with `[📎 name]` placeholders for inline images. A file that fails to parse is reported immediately and excluded — the rest of the batch still proceeds
4. **Boilerplate cleanup step** (`EmailCleanupSession`, `workspaceState('jira.session.emailCleanup')`, kind `email-cleanup`; see `docs/plans/2026-09-30-0905-feat-email-boilerplate-cleanup-plan.md` KTD8). `detectPatternBlocks()` (`src/utils/emailBoilerplate.ts`) runs the `ticketSidekick.email.boilerplatePatterns` entries over each body (without an end phrase, a header covers the line(s) its start phrase is on — add an end phrase for multi-line headers; with one, a block takes the tightest span: the last start occurrence before the end phrase, and an entry whose start equals its end matches that single occurrence). Then: a non-empty email with no match that fits `MODEL_CHECK_MAX_CHARS` → **consent** screen (`model check` / `skip model`); on `model check` each listed email gets one `withLmRetry` call (`buildModelCheckPrompt` → `parseModelCheckReply` → `verifyModelBlocks`; failures log metadata only, never body or reply text; a cancelled chat request stops the loop, leaves unchecked rows `awaiting-consent` rather than `failed`, and keeps the session at consent instead of continuing). Anything detected → **preview** (`strip` / `keep` / row-id exclusion toggles / `save <n>` for model-found blocks, which appends `buildPatternFromBlock()` to the global setting). The preview also offers `model check` (`listModelCheckEligibleRows()` in `src/participant/session/emailCleanup.ts`): the same per-email pass over every row that is not excluded, has a non-empty body within `MODEL_CHECK_MAX_CHARS` and is not yet `checked` (`declined` and `failed` rows included, pattern-matched rows too). `verifyModelBlocks()` returns pattern and model blocks together, so a repeat of a pattern block merges (the pattern wins); a failed call leaves the row's existing blocks untouched; `remapSavedBlocks()` re-points `savedBlocks` by block identity because new blocks can shift the preview numbering. A cancelled chat request keeps the preview, with unfinished rows unchanged. Nothing detected and nothing to ask, or `skip model` with nothing detected → skipped. `strip` runs `applyBoilerplateCleanup()` on the included rows, which also drops inline images referenced only in stripped text. The Command Palette stores a `pending` session and the chat turn it opens runs detection, since the model is only reachable from a chat request
5. `EmailTemplateSelectionSession` stored in `workspaceState('jira.session.emailTemplateSelection')`; chat opened (or continued) with the template/issue-type picker — **one shared template/issue type for the whole batch**, not a per-email choice
6. `EmailReviewSession` stored in `workspaceState('jira.session.emailReview')` — the review table lists every email's subject and non-inline attachment names; an email batch only ever has a New group, so it opens straight on the New screen (no overview, see "Overview and group screens"); user replies **ok** / `create tickets` / a list of row ids to toggle inclusion / `include all` or `exclude all` (see "Bulk include/exclude") / `done`
7. On **ok** / `create tickets`, one ticket is created per included email (skip-and-continue: a single email's creation failure is reported and does not stop the rest), each with `buildEmailJiraWiki(markdownBody)` as the description and its own attachments uploaded afterward; if `ticketSidekick.email.deleteEmlAfterImport: true`, the source `.eml` is deleted after each successful creation (non-fatal)

The "add email as a comment to an existing ticket" flow (a ticket key present in the `@jira add email ...` prompt) stays single-file, using `EmailContentSession`/`workspaceState('jira.session.emailContent')` and `handleEmailContentSession`. It runs the same cleanup step (step 4) first, as a one-row `EmailCleanupSession` with a `comment` target that ends in `streamEmailCommentPreview()`; the content session then carries the cleaned body and attachment set, so `addEmailAsComment()` uploads only the attachments that remain.

### `pickEmailOption` helper

`pickEmailOption(n, templates, issueTypes)` in `sessionState.ts` maps a 1-based user reply index to a template or issue type pick. Templates occupy indices 1..N, issue types N+1..N+M. Returns `{ kind: 'template', name, issueType }` or `{ kind: 'type', issueType }` or `null` if out of range.

## OSS/vulnerability report import (Veracode + Waltz) and email

Veracode, Waltz, and email import share one implementation — `src/participant/jira/reportImportHandler.ts` + `src/utils/reportImport.ts` — for session flow, dedup search, the review-table/toggle-reply UX, and batch ticket creation. Each importer supplies only its own parser, config, and ticket-field-building specifics via a `ReportImportDescriptor` passed from its thin wrapper (`veracodeHandler.ts`/`waltzHandler.ts`/`emailHandler.ts`). This means: dedup search is fault-tolerant per chunk and JQL-quoted where an importer has a dedup key (Veracode/Waltz), or skipped entirely where it doesn't (email); a picked template that vanishes before the user replies produces the same warning for all three; all three link to each newly created ticket in the per-item progress output, and any importer may supply an `afterCreate` hook for per-row work after ticket creation (email uses this for attachment upload). A behavior difference between importers on shared ground is a bug, not a feature — see `docs/plans/2026-08-13-001-refactor-consolidate-report-importers-plan.md` for the original Veracode/Waltz consolidation rationale, `docs/plans/2026-09-03-2108-feat-batch-email-import-plan.md` for email's extension of the same pattern, `docs/plans/2026-09-14-1726-feat-veracode-fold-page-stale-plan.md` for same-line folding, paging, and the stale-ticket check, `docs/plans/2026-09-30-0902-feat-import-ticket-updates-parity-plan.md` for the per-row Already-ticketed actions, and `docs/plans/2026-09-23-1400-feat-report-import-overview-hub-plan.md` for the overview and per-group screens, and `docs/plans/2026-09-27-1949-feat-stale-ticket-target-pick-plan.md` for the close-time target pick on the Stale screen.

The "New — will create" section no longer pre-caps at `BATCH_LIMIT` before the session is built (Veracode and Waltz alike) — it holds every matched "new" candidate and is **pageable** (see "Paging the New section" below); the "Already ticketed" section is unaffected, shown in full as before. Both importers also run a **reverse stale-ticket check** on every import (see "Stale-ticket detection and inline close" below).

### Veracode report import

Users export a Detailed Report XML from Veracode and import it via the VS Code command or directly from chat (`@jira import veracode report`).

1. Command Palette → **Ticket Sidekick: Create Jira tickets from Veracode report (.xml)** (or trigger from chat, which opens its own file picker)
2. `parseVeracodeReport(xml)` (own parser, `fast-xml-parser`-based) extracts all `<staticflaws>` entries; rejected up front if the file exceeds `ticketSidekick.veracode.maxReportSizeMB` (default 50 MB, configurable 1–200 MB) or contains a `<!DOCTYPE`/`<!ENTITY` declaration. `issueId` and `cweId` are each validated numeric (`ISSUE_ID_PATTERN`/`CWE_ID_PATTERN`) at parse time — a malformed `cweId` becomes `null` rather than surviving into a generated CWE-database URL
3. `filterFlaws()` applies `ticketSidekick.veracode.minSeverity` and `ticketSidekick.veracode.includeRemediationStatuses`
4. `VeracodeTemplateSelectionSession` stored in `workspaceState('jira.session.veracodeTemplateSelection')`; chat opened with `@jira import veracode report`
5. User picks a template or issue type (`pickEmailOption()`, reused from the email flow) → `FieldResolver.resolve()` resolves the template's fields
6. Flaws fold into one review row (see "Finding folding" below) before dedup ever runs: flaws sharing a source file and CWE, or a source file and line, form one group.
7. De-dup search (via the shared `reportImport.ts` primitives): `TicketService.searchTicketsRaw` is called in chunks of 40 issue ids with a quoted `labels in ("veracode-issue-<id>", ...)` JQL clause — a folded group searches for *every* member flaw's label, and a match on any one of them counts the whole group as already-ticketed; a failed chunk is logged and skipped without discarding matches already found by other chunks; matches become the "Already ticketed" group, whose rows each get a proposed action (see "Already-ticketed rows: per-row actions" below)
8. A **reverse stale-ticket search** (see "Stale-ticket detection and inline close" below) runs against the project's other open `veracode`-labeled tickets.
9. `VeracodeReviewSession` stored in `workspaceState('jira.session.veracodeReview')`; the review opens on the overview (or directly on the only group that has rows) — see "Overview and group screens" below. The New group holds every matched candidate and is **pageable** (see "Paging the New section" below) rather than pre-capped
10. On `create tickets` (or **ok**) on the New screen, up to `BATCH_LIMIT` tickets are created via the existing `TicketService.createTicket` — one per included row (one row per folded group, not per flaw; titles, description and labels as in "Finding folding" above), each labeled `veracode`, one `veracode-issue-<id>` per folded flaw, one `cwe-<id>` per distinct CWE among them (merged with any template labels), with a Markdown-authored description (converted to Jira wiki via `markdownToJiraWiki()`, every untrusted field sanitized) covering every folded flaw's own Severity, CWE + link, Description, and Recommendation under its own heading, plus a shared Location and Veracode Issue ID list; each per-ticket progress line links to the created ticket when a Jira base URL is configured. Nothing in the other groups is touched.

#### Finding folding

A fold is a group of findings that becomes one review row and, on creation, one ticket. It is built in two places: automatically when the report is parsed (Veracode only), and by the user on the New screen (both importers). Design and decisions: `docs/plans/2026-10-05-1912-feat-report-import-finding-folding-plan.md`.

**Automatic Veracode fold.** `groupFlawsByLocation()` in `veracodeReport.ts` links flaws that share a source file and a CWE (any line) and flaws that share a source file and a line (any CWE), as a transitive closure, so a flaw is never in two groups. A flaw with no source file never folds; a flaw with no CWE never folds by CWE. The fold runs at parse time, before dedup and paging, so a match on any member's `veracode-issue-<id>` label puts the whole group in Already ticketed. Waltz folds nothing automatically: each component is a one-member group.

**merge / unmerge.** On the New screen, `merge 2 4` combines the named rows on the visible page into one row, whatever their CWE, file, component or version; `unmerge 2` splits a merged row back into its originals. A merge is page-local: only `session.rows` changes, `allRows` keeps the originals (`ReviewRowBase.memberIds` lists them), so moving to another page discards it, and creating the merged row removes every member from `allRows`. Both importers' items are group arrays (`VeracodeFlaw[]`, `WaltzComponent[]`), so merging is concatenation, supplied to the shared handler through the descriptor's optional `fold` capability. Email has no `fold`, so it does not offer the replies.

**Folded ticket.** A folded ticket's title is count-based, never an id list: `OrderRepository.java - SQL Injection (7 findings)`, `OrderRepository.java - 7 findings: SQL Injection, Cross-Site Scripting` for mixed CWEs, `OrderRepository.java +2 files - …` across files; Waltz: `[OSS] netty-codec:4.1.100 +2 components — High`, keeping the ` — <rating>` suffix a rating-rise `update` rewrites. Titles are clamped to 255 characters by trimming only the file or component name. The description opens with a banner and an overview table (one row per finding, always complete), then one section per finding with its own location; when it would exceed 30,000 characters, per-finding text is shortened and a note says so. Labels are the union of the members' (Waltz: every component label, every CVE label, one `oss-rating-<highest>`). A one-member group renders exactly as before folding existed.

**add … to <KEY>.** `add 2 4 to PROJ-123` adds New rows on the visible page to any existing ticket, including one Ticket Sidekick did not create. The bare command reads the ticket and shows its summary and status, a warning if it is resolved, the overwrite warning with the findings a rewrite would drop, and two links that resend the command with `as comment` or `as rewrite`; clicking one is the confirmation (no session state). **Comment** adds the record labels (a Waltz rating label already on the ticket is left alone) and posts one comment listing the added findings; the description and title stay. **Rewrite** regenerates summary, description and labels (`TicketService.rewriteTicket`, one `updateIssue`) from the added rows plus every Already-ticketed row whose target is that ticket, then posts a comment listing what was added and naming findings the ticket recorded that the new description no longer covers (Veracode by issue id, Waltz by component label). Ticket text read from Jira is neutralized before it is shown in the prompt. A failed write keeps the rows in New; a comment that fails after the write is reported and the rows still leave New.

**rewrite on Already ticketed.** Every Already-ticketed row also offers `rewrite`, which rebuilds the target ticket the same way. It is all-or-none per target ticket: `apply` stops with nothing written if only some of the unfinished rows pointing at one ticket are on `rewrite`, and the per-reply `BATCH_LIMIT` never splits one ticket's rows. Merges are not remembered between imports, so a ticket built from a merge shows up as several Already-ticketed rows; `rewrite` on all of them rebuilds it.

#### Bulk include/exclude (all three importers)

The New screen offers two bulk controls — **`include all`** and **`exclude all`** (links rendered under the New table, shown only when at least one New row exists) — that set every New row on the currently visible page to included or excluded in one action, instead of toggling rows one at a time. They live in the shared screen renderer (`buildNewGroupScreen()`), so all three importers get them with no per-importer gating. The reply tokens are exact-match only (`parseBulkNewRowReply()`, checked by `parseNewGroupReply()` after the create/exit words and page-nav, before row-id parsing) and verified disjoint from every other reply vocabulary. Like a per-row New toggle, a bulk set is **page-local**: it touches `session.rows` only, never `allRows`, so navigating away from a page and back resets that page's New rows to default-included; other groups and pages are untouched. The one exception: when `create tickets` runs, the visible page's exclusions are written into `allRows` first, so an excluded row stays excluded afterwards.

#### Already-ticketed rows: per-row actions (Veracode + Waltz)

The dedup search reads every result page of each label chunk (`fetchAllPages()`, capped at 1000 tickets per chunk) and keeps every ticket per dedup key (`findAlreadyTicketed()` returns a `DedupMap` of `DedupTicket` lists with labels, resolution, creation date and status). For an already-ticketed item, `buildReviewRows()` unions the labels of all its tickets, asks the importer's `changeTracking.describe()` what changed, and picks the row's **target**: the newest unresolved ticket (latest `created`, ties to the highest key number), or the newest ticket when all are resolved (`pickTargetTicket()`).

A change is a finding id none of the item's tickets record — a Veracode flaw's `veracode-issue-<id>` label, or a Waltz CVE's `oss-cve-<id>` label — or, for Waltz, a worst rating higher than the recorded `oss-rating-<rating>` label. A Waltz ticket with neither kind of record label (created before this feature) is a **baseline**. New Waltz tickets get these record labels at creation.

`deriveTicketedActions()` is the shared five-action policy. Veracode and Waltz both replace it with `deriveRewriteActions()` (see "Rewrite action policy" below), so no current importer uses it; it stays the default for an importer whose change tracking has no `deriveActions`. It sets each row's allowed actions and default:

- no change → `leave` (offers `rewrite`, `re-create`, `leave`; `rewrite` is offered on every row, see "Finding folding")
- change, some ticket open → `update`
- change, every ticket resolved → `follow-up`, or `update` when the only change is a rating rise
- baseline → `update`, which records the current labels only — no comment, no summary change

`follow-up` is offered only with new findings. The Action cell shows every allowed action as its own link with the current one in bold. The user changes a row with `<row id> <action>` or `all <action>` and replies `apply` (or `ok`); `update tickets` / `re-create tickets` (and the legacy `update existing tickets`) run only the rows set to that action. At most `BATCH_LIMIT` rows run per reply.

- **update** (`TicketService.updateLabels()`, one read-merge-write): adds the missing record labels, replaces any old `oss-rating-*` label when it adds a new one, rewrites a Waltz summary ending in ` — <old rating>` (optionally followed by ` (follow-up to <KEY>)`), then posts one comment listing the new findings and any rating rise. A summary the user renamed is left alone and the comment says so. A comment that fails after the labels were written is reported as "labels updated, comment failed".
- **follow-up**: creates a ticket with only the new findings (summary suffix ` (follow-up to <KEY>)`) and links it "Relates" to the target (`TicketService.linkIssues()`). A failed link keeps the ticket and shows a warning.
- **re-create**: creates a full ticket as for a New row.

**Rewrite action policy (Veracode and Waltz).** Both importers supply `changeTracking.deriveActions` (`deriveRewriteActions()` in `reportImport.ts`; `deriveWaltzActions()` delegates to it), which replaces the five-action policy above; email is untouched. A Veracode `new ticket` is built from the row's whole group with the same ` (follow-up to <KEY>)` title suffix, and `update`, `follow-up` (as a new-findings-only ticket) and `re-create` are not offered for Veracode (a typed `update` is answered with the actions the row offers). `deriveActions` switches on the full-ticket `new ticket` and the shared `rewrite` default (`alignRewriteDefaults`); reading target descriptions, the dropped-member pass and `labelsToRemove` are behind `changeTracking.readsTargetDescriptions`, which only Waltz sets, and the Veracode Due Date backfill is behind `changeTracking.dueDateBackfill`, which only Veracode sets (see "Due dates from the SLA table (Veracode)"). Waltz specifics: A Waltz row offers `rewrite` and `leave`, plus `new ticket` (the internal id stays `follow-up`, shown through `changeTracking.actionLabels`) only when every ticket is resolved. `update` and `re-create` are never offered, so typing one gets the usual "can't be set to" answer.

| Situation | Offered | Default |
| --- | --- | --- |
| No change | `rewrite`, `leave`; plus `new ticket` when every ticket is resolved | `leave` |
| Change or baseline, some ticket open | `rewrite`, `leave` | `rewrite` |
| Change or baseline, every ticket resolved | `rewrite`, `leave`, `new ticket` | `new ticket` |

A Waltz **change** is a new CVE, a higher rating, a difference in the recorded remediation dates, or a component that left the ticket's report. `new ticket` is a *full* ticket (the component's whole current content and dates, all record labels, the Due Date), titled with the suffix ` (follow-up to <KEY>)` and linked Relates to the resolved ticket; it is also offered on a row with no change. After the rows exist, `alignRewriteDefaults()` makes every row of one target ticket default to `rewrite` when any of them does, because `rewrite` rebuilds a whole ticket and an Apply that covers only some of its rows is refused. On the first import after the dates feature, every open ticket whose component now has dates defaults to `rewrite` and every resolved one still in the report defaults to `new ticket`; Apply runs at most `BATCH_LIMIT` actions per reply, so repeat it.

**Recorded dates and dropped members (Waltz).** The dedup search cannot carry the description (on Jira Cloud it comes back as ADF), so after it `buildImportReview()` reads each distinct target ticket once through `TicketService.getIssue` (`readTargetDescriptions()`, 8 at a time) and stores the wiki text on `DedupTicket.description`; the texts are kept on the session (`ticketDescriptions`) so a reload or `accept component` does not read them again, until this session rewrites, adds to or merges a ticket. A read that fails leaves the description unread, which skips the date comparison for that ticket's rows and marks the review degraded. `parseRecordedDates()` (`waltzDates.ts`) reads the policy date, planned date and attestation date out of the "Remediation dates" section or, on a folded ticket, out of the component's own overview-table row; no section, an unreadable table or a missing row is "no recorded dates". The section's headings and column titles are shared constants used by the builder and the reader, and a round-trip test guards them. The plan status is shown but never compared, because it moves with the clock. A ticket created before the feature records no dates, so it counts as changed once the report has dates for it, open or resolved. The same holds for the attestation date of a ticket whose table still has the old column title "Plan deadline": the reader (`COLUMN_ATTESTATION`) matches only the current title, the other two dates still read, and the ticket reads as changed until a rewrite records the new title. A member counts as **dropped** (`applyDroppedMembers()`) only when the target ticket carries its `oss-dep-*` label, no row points to the ticket for it, and it is absent from the *unfiltered* report (`ReviewSession.reportKeys`); a component only filtered out by the rating/action settings or accepted keeps its label. A rewrite then removes the labels of dropped members in the same write (`rewriteTicket`'s `removeLabels`, `labelsToRemove()`).

**Paging.** The Already-ticketed table shows 20 rows per page (`GROUP_PAGE_SIZE` in `importScreens.ts`, the same size as Stale; `ReviewSession.ticketedPage`, independent of the New and Stale pages). `next`/`prev`/`page <n>` are parsed ahead of the row/action replies and clamp at the ends; the page is clamped again at render time, so rows removed by an `accept component` never leave it past the last page. Paging only slices what is rendered: `<row> <action>`, `all <action>`, `apply`, the shortcuts and their counts read every row in `allRows`, so a row on another page can be set and one ticket's `rewrite` rows are never split by a page boundary. A finished row shows its result in place of links and is skipped by later runs; a failed row keeps its links for a retry. Email has no change tracking and keeps its screen unchanged. See `docs/plans/2026-09-30-0902-feat-import-ticket-updates-parity-plan.md`.

#### Due dates from the SLA table (Veracode)

Plan: `docs/plans/2026-10-23-0638-feat-veracode-sla-due-dates-plan.md`. The pure logic is in `src/utils/veracodeDates.ts`.

- **Policy.** `ticketSidekick.veracode.slaDays` maps the six severity names to calendar days (default Very High 14, High 28, the rest 0). `resolveSlaDays()` matches names ignoring case and spaces; 0 means no date; a known severity with an invalid value gets no date (not the default) and an unknown key changes nothing, both returned in lists that `veracodeHandler.ts` logs once per import at session build (`jira.veracode`, warn). An undefined, null or non-object setting means no policy.
- **Dates.** `parseVeracodeReport` reads `date_first_occurrence` into `VeracodeFlaw.firstFoundDate` (`toCalendarDate()`, the date as written, no time zone shift). `flawDueDate()` is that date, else the fallback start, plus the severity's days; `groupDueDate()` is the earliest over a group. The fallback start is the import date for a new ticket (`localDate()`) and the Jira `created` date of the ticket being rewritten or backfilled, so it does not move between imports.
- **Ticket content.** The Findings table gains `First found` and `Due date` columns; the slim table does not and its note says so. The reader needs no change: it finds the table by its `Issue ID` and `File` titles and ignores columns it does not use.
- **Write paths.** `buildTicketFields` and `buildFollowUp` return `duedate` (after the template fields, marked `optionalFields`) only when some flaw has a due date. A rewrite does not use that value: the descriptor's `rewriteDueDate` decides (`writeRewrite`): an empty current Due Date gets the earliest over the whole ticket, otherwise only flaws joining the ticket (`add … as rewrite`, or the new findings of `rewriteTicketedGroup`) can move it, and only earlier; anything else sends no `duedate` (Waltz's hook overwrites with the regenerated group's date). A Due Date is therefore set once and a hand-edited one is never overwritten. `add … as comment` never writes it. The refusal fallback is Waltz's (`refusedFieldsOf`, `droppedFields`). `descriptor.dueDateNote` words the result line.
- **Detection.** The dedup search requests `duedate`; `DedupTicket.dueDate` is null when empty and undefined when the search did not return the field. `applyMissingDueDate()` (enabled by `changeTracking.dueDateBackfill`) marks an open target with a null Due Date where any row of the ticket has a flaw with a due date as changed (`due none→<date>`, `DateKind` `due`), the same earliest date on every row of the ticket and derives its actions again; it runs before `alignRewriteDefaults()`. A ticket with any Due Date, a resolved target and a ticket none of whose rows has a due date are never flagged. The date shown is the ticket-level date `rewriteDueDate` writes, except that the preview counts the report's rows only.
- **Overview and export.** `overviewExport.dueDateOf` returns `groupDueDate()` with today as the fallback start; `@jira /overview` is unchanged because it reads the Jira field.

#### Known limitation

The multi-step vulnerability data-path trace shown in Veracode's web UI ("Injection Point → ... → Flaw") is **not present** in the Detailed Report XML format — confirmed by full XSD schema review and empirical inspection of a real report. Only the flaw's own `description` attribute (which sometimes names generic tainted-source APIs, but not the actual call chain) is available and is included (sanitized) in the ticket. Full data-path support would require a different Veracode API/export (e.g. the Findings REST API) and is out of scope for this feature.

### Waltz OSS report import

Users export an "OSS Report" `.xlsx` from Waltz (or a compatible SCA tool) and import it via the VS Code command or directly from chat (`@jira import oss report`).

1. Command Palette → **Ticket Sidekick: Create Jira tickets from OSS report (.xlsx)** (or trigger from chat, which opens its own file picker)
2. `parseWaltzReport(buffer)` (`exceljs`-based — `workbook.xlsx.load()`, which reads the ZIP via `jszip`'s central-directory-first parsing rather than a sequential/streaming reader, so it doesn't choke on real-world exports written by streaming XLSX writers; a prior `read-excel-file`/`unzipper-esm` build threw `Couldn't unzip \`.xlsx\` file contents` on exactly this class of file even though Excel opened it fine — see `docs/solutions/` for the write-up) joins the required `ComponentRemediations` sheet with the optional `VersionInstances`/`Vulnerabilities` sheets on `Component name and version`; guarded by `ticketSidekick.waltz.maxReportSizeMB` (default 50 MB, configurable 1–200 MB) and a `PARSE_TIMEOUT_MS` (15s) hard ceiling. The timeout is a `Promise.race`, not a true cancellation — it bounds how long the user waits before seeing an error on a pathological (e.g. decompression-bomb-style single-entry) `.xlsx`, but the underlying parse keeps consuming CPU/memory in the background after it fires; it does not itself prevent resource exhaustion
3. `filterComponents()` applies `ticketSidekick.waltz.minVulnRating` and `ticketSidekick.waltz.includeRemediationActions`
4. `WaltzTemplateSelectionSession` stored in `workspaceState('jira.session.waltzTemplateSelection')`; chat opened with `@jira import oss report`
5. User picks a template or issue type (`pickEmailOption()`, reused from the email flow) → `FieldResolver.resolve()` resolves the template's fields
6. De-dup search (via the shared `reportImport.ts` primitives): `TicketService.searchTicketsRaw` is called in chunks of 40 sanitized component labels with a `labels in ("oss-dep-...", ...)` JQL clause; matches become the "Already ticketed" group with per-row actions (see "Already-ticketed rows: per-row actions" above). A dedup-search failure degrades gracefully (empty dedup map + warning) rather than aborting the import
7. A **reverse stale-ticket search** (see "Stale-ticket detection and inline close" below) runs against the project's other open `oss-dependency`-labeled tickets.
8. `WaltzReviewSession` stored in `workspaceState('jira.session.waltzReview')`; the review opens on the overview (or directly on the only group with rows) exactly like Veracode's — see "Overview and group screens" below. The New group holds every matched (not-yet-ticketed) component and is **pageable** (see "Paging the New section" below) rather than pre-capped
9. On `create tickets` (or **ok**) on the New screen, up to `BATCH_LIMIT` tickets are created via the existing `TicketService.createTicket` — one per included component, labeled `oss-dependency` + a sanitized, hash-suffixed component label + one `oss-cve-<id>` label per CVE + one `oss-rating-<rating>` label (merged with any template labels), with a Markdown-authored description (converted to Jira wiki via `markdownToJiraWiki()`) covering max vuln rating, the single most critical CVE, affected artifacts (capped at 25, "+N more"), and a "Known vulnerabilities" table (capped at 10, "+N more"). A component the user merged with others (see "Finding folding") becomes one ticket with the folded title, banner and overview table instead. Nothing in the other groups is touched.

#### Remediation dates and the Due Date (Waltz)

Plan: `docs/plans/2026-10-22-1929-feat-waltz-due-dates-plan.md`. The pure date logic is in `src/utils/waltzDates.ts`.

- **Columns read.** From `ComponentRemediations`: `Expected Remediation` (policy date), `Remediation Target Date` (planned date, present on `Remediate` rows), `Attested Rem Plan Due By` (attestation date) and `Reason, where plan invalid` (the report's own plan status, for example Overdue or Unplanned). From `ReportDetails`, a sheet of label and value pairs with no header row, the `Extracted On` value (the plan status is labelled "as of" that date). All are optional, so an older export still parses. The report's overrun-days column is never read: it is 0 for a component without a plan, which would hide the ones that need attention most, and no overdue-days number appears anywhere. Dates are `YYYY-MM-DD` strings end to end (`toCalendarDate()` accepts text or a date cell and drops any time), and the parser logs only the count of unreadable date cells (`jira.waltz`, never a value).
- **Ticket content.** A single-component description gets a "Remediation dates" section after the rating (policy date, planned date, attestation date, plan status), or "Not reported yet." with no dates. A folded or merged ticket adds the same four columns to its overview table, one row per component, `n/a` where a member has none, and does not repeat them per component.
- **Due Date.** The planned date, else the policy date; a folded or merged ticket takes the earliest of its members, and none is set when no member has a date (never cleared). It is written after the template fields, so a template cannot override the report, by create, `rewrite`, `add … as rewrite`, `new ticket` and the merge survivor. `add … as comment` and the Stale close never touch it. A rewrite overwrites a hand-edited Due Date when the report has one, and the result line says so.
- **Refused Due Date.** Jira may not have the field on a project's screen. The builders mark it `optionalFields`; `TicketService.createTicket`/`rewriteTicket` repeat the call once without it when a 400 names it under `errors` (`refusedFieldsOf()`, keyed on the field name, not the message), return `droppedFields`, and the caller shows a warning and logs it. Any other error is rethrown. Not verified against a live Jira: see the register.
- **Rewrite comment.** It lists each component's changed dates (`policy 2026-12-31 → 2027-03-31`) and the Due Date it set.

#### Accepted CVEs and components (Waltz)

`.jira-oss-accepted.json` in the workspace root holds `{ "accepted": [...] }`. An entry is `{ component, cve?, version?, reason? }` (`docs/plans/2026-10-20-1847-feat-waltz-accepted-components-plan.md` KTD1). With a `cve` it is a **CVE pair** the team decided to live with, matched on component name only (`docs/plans/2026-10-06-1321-feat-waltz-accepted-cve-list-plan.md`). Without a `cve` and with a `version` it is a **component entry**: one exact component name and version accepted as a whole. An entry with both is read as a CVE pair and the version is ignored; one with neither is skipped with a warning.

- **Where CVE pairs apply.** `continueAfterImportIssueType` passes a narrowing hook to `buildReviewRows` (`src/utils/reportImport.ts`), which runs it only on items the dedup search found no ticket for, before the row id is assigned. `session.items`, `rawItems`, the dedup search and the stale check keep the full report. The hook comes from the descriptor's optional `accepted` capability (`ImportAccepted`); Veracode and email omit it.
- **Where component entries apply (KTD3).** *New:* `narrowGroup` drops accepted members before any per-CVE logic and counts them in `hiddenComponents`. *Already ticketed:* a second `buildReviewRows` hook (`dropTicketed`) drops an item the list accepts as a whole before its `A` id is assigned, so the surviving ids stay contiguous; open and resolved tickets alike (KTD4). *Stale:* `buildWaltzActiveComponentPredicate` takes the entries and treats an accepted component as inactive, so a ticket covering only accepted components is flagged by the existing "stale only when every id is inactive" rule.
- **Matching and narrowing** (`src/utils/waltzAccepted.ts`, pure). The component name is `nameVersion` up to its last `:`, the version what follows it; both compare trimmed and case-insensitively (KTD2). CVE ids compare upper-cased. A component that lost no CVE is returned untouched. One that lost some is rated by the highest `overallSeverity` of what is left (the report rating is kept when none of them carries a severity) and hidden when that is below `ticketSidekick.waltz.minVulnRating`; one that lost all is hidden.
- **File handling** (`src/services/AcceptedListService.ts`). Reading is fail-open: a missing file is an empty list, an unreadable one hides nothing and shows a warning. Writing never overwrites a file that could not be read in full (invalid JSON, or an entry skipped with a warning). An older extension version skips component entries with that warning and so refuses to write.
- **Session state.** `ReviewSession.acceptedHidden` (`{ cves, belowFloor, components? }`) records what was hidden, so the overview — or the only group's screen, when the import has no overview — can say so. `ReviewSession.staleCandidates` keeps the open marker-labeled tickets the stale search did not flag, with the dedup ids still active for each (`findStaleTickets` returns them as `pending`); only importers with an `accepted` capability store it. The session schema version is 12 (it is one shared constant, so the bump expires every in-flight multi-turn session).
- **Replies.** `accept <rows> [because <reason>]` on the New screen accepts the rows' CVEs. `accept component <rows> [because <reason>]` on the New screen (row numbers) and the Already ticketed screen (open `A` rows) accepts the rows' components at their version; plain `accept` on Already ticketed is answered with the usage. `accepted`, `unaccept <n>`, `unaccept <component> <CVE>` and `unaccept-component <component> <version>` (what the list's Remove links send) work on the overview, the New screen, and the only screen of a single-group import. `acceptRows` and `acceptComponents` in `importAccept.ts` share `applyAcceptedList`, which narrows every New row in `allRows` again, drops accepted Already-ticketed rows, and narrows merged rows that were not named so their ticket content matches; a merge whose member vanished falls back to its remaining originals. A failed write or a missing workspace leaves the session unchanged.
- **`unaccept` keeps the screens in step (Waltz).** A removed entry used to wait for the next import. The review now stores its report path (`ReviewSession.reportFilePath`) and, after a successful `unaccept`, rebuilds itself from that file when `hasUnfinishedChoices` is false, or sets `outOfDate` when it is true (see "Merging tickets (Waltz)" → "Staying in step"). `accept` keeps its in-place narrowing.
- **Stale refresh after `accept component` (KTD5).** `moveCandidatesToStale` matches the accepted rows' dedup keys (`descriptor.dedupKeyOf`) against the stored candidates. A candidate whose every remaining active id is accepted is grouped by `buildStaleTicketGroups` and merged into the existing Stale list (tickets already there keep their selection and closed state), and the Stale group is added to the overview. No second Jira search runs; the raw report is not needed at reply time.

#### Merging tickets (Waltz)

Related Waltz tickets are combined with `merge <sources> into <survivor>` on the overview and the Already ticketed screen. Plan: `docs/plans/2026-10-21-0949-feat-waltz-ticket-merge-plan.md`.

**Grammar.** `merge A5 A6 into A3` or `merge PROJ-15 PROJ-18 into PROJ-12`; each side is an `A` id (finished rows included, resolved to `ticketedTargetKey(row)`) or a ticket key. `parseOverviewReply` and `parseTicketedGroupReply` match it ahead of the generic row-action matcher; the New and Stale parsers answer the form with a pointer to the overview, so `merge 2 4` keeps combining New rows. The importer switches it on with the descriptor's optional `ticketMerge` capability (Waltz only), which also turns on `reload report` and the refresh after `unaccept`.

**Confirmation (stateless).** The bare command (`showMergePrompt`, `importMerge.ts`) resolves the sides with `resolveMergeSides` (`src/utils/ticketMerge.ts`), reads every ticket and shows `buildMergePrompt`: the tickets, the steps, and the warnings (R10: a resolved survivor, a ticket without the importer's marker label, an already-resolved source) and fallbacks (R9: no Duplicate link type, no Duplicate resolution). The reply is refused, with nothing written, for the same ticket on both sides, an unknown id or malformed key, more than `BATCH_LIMIT` (50) sources, or when no report row points to the survivor or any source. Its single link resends the command with the resolved keys plus `confirm`; clicking is the confirmation, as with `add … as rewrite`.

**Steps, in order.** `buildMergePlan` lists them and `ReviewSession.mergeRun` records their status:
1. `survivor-rewrite` — `planRewrite` over the survivor's rows plus the sources' rows, then `writeRewrite`; the findings the new text no longer covers are kept for the comment.
2. `survivor-comment` — the importer's preface (`ticketMerge.buildCommentPreface`, naming the absorbed tickets) plus `fold.buildComment`.
3. Per source, `link` — `TicketService.linkIssues(source, survivor, 'Duplicate')` (the source is the outward "duplicates" side), skipped when `hasLinkBetween` finds one; `Relates` when the instance has no Duplicate link type (`getIssueLinkTypes`) — then `source-rewrite` — `TicketService.markTicketMerged`: `[Merged into KEY]` summary prefix (old summary trimmed to 255 characters) and a `{panel}` banner above the unchanged description, each applied once.
4. Per source, `close`, last. The sources are grouped by issue type through `buildStaleTicketGroups` and the user always picks the target status (cleanup-rule targets first, then the reachable statuses; a rule contributes its target state, not its resolution). The resolution is the project's Duplicate resolution when `getResolutions()` offers one; otherwise the stale close's resolution pick (with `none`). Transitions run through `transitionTickets`, and each closed ticket is read back: `transitionAlongPath` retries without the resolution when Jira rejects the field, so a ticket that does not show the requested resolution is named in the final report as closed without it. An already-resolved source skips only this step; a source with no discovered workflow is reported as not closed, with the `@jira discover workflow` hint.

**Failure handling.** A failed step stops the run (`awaiting: 'decision'`), reports every ticket as a link with each step's status and the error, and offers `retry` (the failed step runs again; finished steps do not) or `ignore` (the step is skipped and the rest runs); `cancel` ends the merge and keeps what is done. The run's replies (`retry`, `ignore`, a numbered or named pick, `cancel`) are read by `parseMergeRunReply` before the screen's own vocabulary, so no extra session kind or router entry exists. The survivor comment is skipped when it is already on the ticket (`hasCommentStartingWith`), so a re-sent `confirm` does not post it twice. A merge that ends with a missing step marks the screens out of date instead of refreshing them.

**After the merge.** Source rows show "merged into KEY" (`TicketedRowResult` action `merge`), the survivor's rows show rewritten, `ImportOutcomes` counts `merged` (close done) and `mergeFailed` (any source with a missing step), and the final report lists what is missing.

**Staying in step.** `ReviewSession.reportFilePath` is set by both entry points (the command palette passes the picked path; the chat picker returns it) through `buildImportTemplateSession`. `buildImportReview` holds the dedup search, the rows and the stale check and is shared by the first import and by `refreshReview`, which re-parses the file with `descriptor.parseAndFilter`, keeps the issue type, template, fields and outcomes, recomputes `groups` and `singleGroup`, clamps the three page indexes and keeps the previous view only while the review keeps its shape. `hasUnfinishedChoices` decides between refreshing at once and setting `ReviewSession.outOfDate`: a New row excluded or merged in `session.rows` (page-local; `allRows` keeps the defaults), or an unfinished Already-ticketed row whose `action` differs from its recorded `defaultAction`. After a finished merge and after `unaccept` the rule applies.

**Reload report.** `reload report` (overview, or the only screen of a single-group import) states what it will do and what would be lost; its link sends `reload report confirm`, which refreshes from the stored file. A file that is gone is reported and the same file picker as the import opens: a chosen file replaces `reportFilePath` before the refresh, a cancelled pick changes nothing. A report that no longer parses is reported and the review stays as it was.

**Later imports.** Nothing is stored. The survivor carries the union of the labels and is open, so it is the target; the cancelled ticket keeps its marker labels but is resolved, so it never wins.

#### Duplicate open tickets and Veracode ticket merge

Plan: `docs/plans/2026-10-23-2042-feat-duplicate-open-tickets-merge-plan.md`.

**Ticket cell.** `buildReviewRows` records `ReviewRowBase.openTicketKeys`: the tickets other than the target that carry one of the row's keys and have no resolution (the `resolved` flag). `ticketedTicketCell` shows `<target> · also open: KEY[, KEY…]` (three keys, then `+N`). A row saved before the field existed shows the target alone. `ticketKeys` is unchanged and still feeds change detection and target choice (closed tickets' labels keep their items known).

**Hint.** With `canMergeTickets`, the Already ticketed screen shows a merge reply built from the first unfinished row with an open extra ticket (`merge <other> into <target>`, with a note that swapping the two keeps the other), else the generic form.

**Close mode.** `ImportTicketMerge` is a union: Waltz keeps the rewrite mode above (survivor rewrite and comment, per-source link and `markTicketMerged`); Veracode sets `mode: 'close'` with `itemNoun` and `buildSourceComment` (`buildMergedSourceComment` in `veracodeReport.ts`, numeric flaw ids only). The same engine (`importMerge.ts`) runs both: confirmation click, status and resolution questions, `retry`/`ignore`, final report.

- `analyzeSourceMoves` (`ticketMerge.ts`) reads each source's labels through the descriptor's `labelToDedupKey`. Keys only the source records are `movable` when the rewrite plan still covers them and `unlisted` when `planRewrite` reports them dropped (the report no longer lists them). The same analysis feeds `buildCloseMergePrompt` and the run (`MergeRun.sourceMoves`).
- `buildCloseMergePlan` lists the steps: `survivor-rewrite` only when some source has movable items, then per source `link` (type fixed per step: `Relates` if items moved, else `Duplicate`, falling back to the other type when the project lacks the wanted one) and `source-comment` (idempotent: skipped when a comment starting with the same line exists), then the `close` steps.
- The Veracode survivor rewrite passes the kept ticket's creation time and Due Date to `writeRewrite`, with the movable flaws (cut by `fold.narrowToNew`) as the joining item, so `rewriteDueDate` keeps its set-once, move-earlier rule.
- Items a rebuild does not cover split three ways: `movable` (covered), `unlisted` (not in the unfiltered report: `reportKeysOf` on the Veracode descriptor feeds `ReviewSession.reportKeys`, which close mode now also reads) and `elsewhere` (still in the report but outside the rows the kept ticket is rebuilt from, e.g. filtered by settings or grouped under a third ticket). Neither of the last two is moved; both are named in the comment on the closed source and on the confirmation page.
- `holdSourcesWithoutRewrite` (`importMerge.ts`): when the `survivor-rewrite` step ends `skipped` (a failure answered with `ignore`), every pending step of a source with movable items is skipped too, so those sources stay open and unlinked and the final report lists the skipped steps.
- The source comment (`buildMergedSourceComment`) says the ticket "was merged into KEY", never that it is closed, because it is posted before the close step.
- Closed rows are marked `merge` when their `close` step is done (rewrite mode marks them when the source rewrite is done). `finish` also removes closed sources from `openTicketKeys` on every row that listed them.
- `canMergeTickets` stays one switch, so Veracode also gets `reload report` and the post-merge refresh.

#### Component labels

`sanitizeComponentLabel()` lowercases and hyphenates disallowed separators (dots pass through unchanged, so version numbers like `1.2.3` stay readable), then appends a 6-hex-char SHA-256-derived hash of the *raw* `nameVersion` — this keeps the label human-readable while making it collision-safe as the sole dedup key, since two distinct components (e.g. differing only in a separator character) can otherwise sanitize to the identical readable text.

#### Known limitation

The report's real-world schema (sheet names, column headers) was validated against a single inspected `.xlsx` export; a schema drift in a different Waltz version, report template, or locale would break parsing for some users with no test coverage to catch it in advance — tracked as an open question in the plan doc, not yet validated against a second real export.

### Overview and group screens (all three importers)

The review is split into up to three result groups — **New**, **Already ticketed**, **Stale** — so each kind of result has its own screen, reply vocabulary and action (`docs/plans/2026-09-23-1400-feat-report-import-overview-hub-plan.md`). The `ReviewSession` records which screen is showing (`view`), the groups that had rows when it was built (`groups`, fixed for the session), whether exactly one did (`singleGroup`), and the accumulated action outcomes (`outcomes`); `initImportViewState()` sets them once when the session is built.

- **Overview** (`buildImportOverview()`): one line per group with its count, what already happened to it (e.g. "50 created · 12 left", "1 closed") and an `open new` / `open already ticketed` / `open stale` link while it still has something to act on. A fully handled group stays listed with its outcome and no link. `done` (or a cancellation word) ends the import with a one-line summary of the outcomes.
- **Group screens** (`buildNewGroupScreen()`, `buildTicketedGroupScreen()`, `buildStaleGroupScreen()`): only that group's table and actions — `create tickets` (New), per-row actions plus `apply` (Already ticketed), `close tickets` (Stale) — plus `back` to the overview. After an action the per-item results stream and the overview returns.
- **Single group:** when exactly one group has rows (always the case for email), that screen opens directly, offers `done` instead of `back`, and re-shows itself after an action.
- **Reply parsing:** `parseImportReviewReply()` reads a reply only against the current screen's vocabulary — a row id on the Stale screen or a ticket key on the New screen is "didn't understand", never acted on, and a reply mixing vocabularies is rejected whole. Confirmation words (`ok`, `post it`, …) run the screen's single action: `create tickets` on New, `apply` on Already ticketed, `close tickets` on Stale; on the overview they are not accepted. Cancellation words go back to the overview (or end a single-group import). The command words are pinned disjoint from confirmation/cancellation words, row ids, ticket keys and page/bulk tokens by a unit test.
- **Superseded import:** a reply arriving after a newer import claimed the template-selection key closes the old review without acting (`sessionWasSuperseded()`).

### Paging the New section (Veracode + Waltz)

The "New — will create" review section holds every matched candidate up front (`ReviewSession.allRows` in `sessionState.ts`) rather than pre-capping before the session is built. `buildReviewPage(allRows, page)` slices out one page (`BATCH_LIMIT`, 50 rows) of "new" candidates plus every "already ticketed" row (that section is always shown in full, unpaged). Replying `next` / `prev` / `page <n>` (case-insensitive; `next page`/`previous page` also work) navigates — recognized ahead of the row-id toggle parser, so it never collides with a numeric reply. Each page defaults every one of its rows to included; navigating away discards any toggles made on a page the user has left, and `create tickets` (or **ok**) creates only the currently visible page's included rows — pick which page to create from by paging there first. Created rows then leave the New group, so the next page moves up and a repeated `create tickets` never creates a row twice. A bare numeric toggle only affects a row on the currently visible page; a number matching a row on a different page is unrecognized input, not a silent toggle or page jump. The bulk `include all` / `exclude all` controls (see "Bulk include/exclude") are page-local in the same way. The old "N more matched, re-run the import" message is replaced by "Page X of Y" wording; the per-confirm `BATCH_LIMIT`-tickets cap and its own message are unchanged.

For Veracode, a folded group's full ticket description is built lazily — only for a row the user actually confirms into creation — rather than for every candidate up front, since most of a large report's candidates are never paged to.

### Stale-ticket detection and inline close (Veracode + Waltz)

Every import run also searches the target project for open (`resolution is EMPTY`) tickets carrying the importer's marker label (`veracode` / `oss-dependency`) and flags one stale when every finding it covers is either absent from the current report or present but no longer matching the importer's own remediation filter (`includeRemediationStatuses` / `includeRemediationActions`). A folded, multi-finding ticket is flagged only once *all* of its findings are gone — one still-active finding keeps it off the stale list. `findStaleTickets()` in `reportImport.ts` runs one search per import and reads every result page (100 per page, `fetchAllPages`), up to a safety bound of `MAX_STALE_TICKETS` (1000) open tickets. Data Center pages by `startAt` and a reported `total`, so a server that caps its page below 100 is still read to the end; Jira Cloud's `/search/jql` pages by `nextPageToken` and ignores `startAt`, so the token is passed back through `TicketService.searchTicketsRaw`, and a page that adds no ticket already read ends the read instead of repeating (the dedup search shares this reader). When more matched than were read it says "Checked the first N of M ticket(s) … coverage may be incomplete", and a failed page fails the whole check (no stale section, with a warning) rather than trusting a partial one. Only tickets carrying the importer's marker label are searched, so a hand-made ticket without it never reaches Stale. The Stale screen shows 20 tickets per page (`GROUP_PAGE_SIZE` in `importScreens.ts`, `ReviewSession.stalePage`); `next`/`prev`/`page <n>` move between pages, a ticket key toggles a ticket on any page, and "Close N tickets" counts the selection across all pages. Closing is still capped at `BATCH_LIMIT` (50) tickets per reply.

Stale tickets render on their own Stale screen, one per row with its issue type, toggled by full ticket key (e.g. `PROJ-123`) and defaulting to **unselected** — nothing transitions without an explicit toggle. On `close tickets` (or **ok**) on that screen, the user picks where the selected tickets go (`docs/plans/2026-09-27-1949-feat-stale-ticket-target-pick-plan.md`), through a stepped `StaleCloseSession` stored under `jira.session.staleResolution`:

1. **Issue type** — each run closes one issue type. When the selection spans several, the user first picks which one; the other types' tickets stay selected for a later close.
2. **Target** — every `.jira-templates.json` `cleanupRules` entry matching the project + issue type (listed first, as "rule name → target"), then every status the selected tickets can reach in the discovered workflow, alphabetically. A rule applies its own target and resolution; a plain status (including a non-final one like "Verification") applies only the status. When no rule matches and no selected ticket can reach any status, the close explains why and suggests `@jira discover workflow` instead of asking.
3. **Resolution** — asked once, only when the target is a closing status (`CLOSED_LIKE_STATES`: Done, Resolved, Closed, Won't Fix) and nothing else supplies one. `none` or `skip` sets no resolution.

Replying `back` (or a cancellation word; at the resolution step `skip` means "no resolution" instead) returns to the Stale screen with nothing transitioned. Transition paths are computed only after the pick, from the workflow-graph snapshot stored with the stale section, and run through the same `transitionTickets()` `@jira cleanup` uses (extracted from `cleanupHandler.ts`'s `executeCleanupBatch()` for reuse). A selected ticket already in the target, or with no path to it, is skipped with a note and deselected; a transitioned ticket is marked so a repeated close never transitions it twice. While tickets of another issue type are still selected, the Stale screen stays open after a run. A stale ticket is selectable when its project + issue type has a discovered workflow — no cleanup rule is needed. One with an unknown issue type or no discovered workflow still renders, with a note, but isn't offered as a toggle. The resolution names are fetched once when the stale section is built, so the close makes no Jira call before the transitions. Tickets moved to a non-final status stay open, so later imports list them again as ordinary stale rows.

### Ticket tables and readers (Veracode + Waltz)

Every Veracode description opens with a **Findings** table (`FINDINGS_COLUMNS` in `src/utils/veracodeFindingsTable.ts`: Issue ID, Severity, CWE, CWE name, Module, Path, File, Line, Function, First found, Due date) built by `pushFindingsTable()` in `veracodeReport.ts`, for single-finding tickets too; `fitWiki` never drops it. When even the table-only text exceeds the budget (the full table fits about 110 findings with long function names and paths), one more level swaps in a slimmer table (`SLIM_FINDINGS_COLUMNS`: issue id, severity, CWE, file, line; it also omits the two date columns) with a note saying which columns were left out; the reader accepts it and returns the missing fields as unknown. Past about 600 findings the description still exceeds the budget (KL13). Every Waltz description carries the **Components** table (`COMPONENT_COLUMNS` plus the four date columns, `pushFoldedTable()` in `waltzReport.ts`), and a single-component ticket has it as a one-row table instead of the former "Remediation dates" section. The column titles live next to the readers and are shared with the builders, and round-trip tests build a description and read it back.

The readers, `readVeracodeFindings()` and `readWaltzComponents()`, turn a ticket's description, summary and labels back into per-finding or per-component records in layers: the table, then the older layouts (the previous folded overview table and the one-finding Location block for Veracode; the previous folded table and the "Remediation dates" section for Waltz), then the title and labels. Each record carries a `detailSource` (`table`, `legacy`, `title-labels`; `report` is added by the import export) and an `approximate` flag: the import's sanitizers change unusual characters in names, paths and modules, so text fields are returned as the ticket holds them. Issue id, CWE id, severity, line, ratings and dates are exact. A Veracode table whose ids differ from the `veracode-issue-<id>` labels, or a Waltz table with a different number of component labels than rows, sets `edited`. `src/utils/wikiTableRead.ts` holds the shared wiki-table helpers (`parseRecordedDates` uses them too). The exact raw-data block (a `{code}` JSON block or an issue property) is deferred; KL19 tracks the approximation.

### Security overview (Veracode + Waltz)

`src/utils/securityOverview.ts` is the pure model: `buildOverview()` groups tickets (`OverviewTicket` from `TicketService.listOverviewTickets()` or `getOverviewTicketsByKeys()`) by their earliest Fix Version, with release dates from `TicketService.getProjectVersions()` and descriptions from `readDescriptions()` (8 at a time; a failed read leaves the ticket at the title-and-labels layer). Flags: `overdue` (Due Date before today) wins over `due-before-release` (Due Date before the Fix Version's release date); no flag for a later Due Date or an undated Fix Version. Counts, row order (flag, Due Date, key), the Not assigned table and the Jira link per table are derived there (`jiraFor()`: a label-and-Fix-Version query for the standalone export, an explicit key list for an import export, falling back to the label query above `JQL_KEY_CAP` keys; all queries use `resolution is EMPTY`). `renderOverviewMarkdown()` neutralizes every Jira and report value; `src/utils/securityOverviewCsv.ts` writes the CSV (BOM, one row per Veracode finding, one per Waltz ticket, `csvCell()` prefixes a cell a spreadsheet could read as a formula). `ticketSidekick.jira.overviewCsvDelimiter` picks the separator.

Entry points: `@jira /overview [PROJECT] [csv]` (`src/participant/jira/overviewHandler.ts`, routed in `JiraParticipant.ts` before the LLM intent parse; the "Save as CSV" link is a full re-run command, so no state is stored) and the `export` / `export csv` replies of an import (`src/participant/jira/importExport.ts`, enabled by the descriptor's `overviewExport` capability; Veracode and Waltz, not email). The import export takes the open targets of the Already-ticketed rows (tracked), the Stale tickets (stale) and the New rows plus the Already-ticketed rows whose tickets are all resolved (in report, no ticket), uses the report's own records as the exact detail, and changes nothing in the review session. `export` works on the overview and on the only screen of a single-group import; on a group screen of a multi-group import it says to go back first. The overview and a single-group screen show an **Export** link (`canExport` in `ImportScreenOptions`, set from `overviewExport`). The reply ends the turn on the export: `reportImportHandler.ts` does not re-render the review, it saves the session and returns the review's session kind, and `importExport.ts` closes the output with `buildExportFollowUp()` (a `Back to overview` or `Done` link), on every path including a failed Jira read.
